Web - Status

Health Check API

One GET reports whether the service considers itself operational, and hands back the server's own high-resolution clock reading alongside the verdict. Two fields, no body to send, nothing to authenticate.

  • No API key
  • Single GET
  • Server clock included
  • Monitor friendly

Poll service health

GET/health

https://aisenseapi.com/services/v1/health

Check the service

curl https://aisenseapi.com/services/v1/health
{"status":"ok","microtimestamp":1787172036.878165}

HTTP 200 with a JSON body. No headers to set, no query string, no request body. That makes it safe to paste straight into a monitoring tool that only accepts a URL.

Response fields

FieldTypeDescription
statusstringok when the service considers itself able to serve requests. Anything else, including no response at all or a body that fails to parse, should be treated as not operational.
microtimestampnumberUnix time in seconds with a microsecond fraction, read from the server's clock as the response was built.

Why the timestamp is there

A status field on its own tells you what some machine thought at some point. The timestamp turns that into a claim you can check.

  1. It proves the answer is fresh

    A cached copy carries the timestamp of the moment it was first built, not the moment you asked. If the number barely moves between two polls taken seconds apart, something between you and the service is answering on its behalf and the green check means nothing. Compare consecutive readings and a stale proxy gives itself away.

  2. It exposes clock skew

    Subtract the value from your own clock at the moment the response lands. The difference is round trip time plus the drift between the two machines. Round trip is tens of milliseconds; anything larger is drift, and drift is the kind of fault that hides until it breaks something.

  3. It costs nothing to collect

    You are already polling for status. Recording the delta alongside it turns an up-or-down check into a running measurement of how far apart your systems believe the time to be.

Read both clocks in one line and compare:

curl -s https://aisenseapi.com/services/v1/health; date +%s.%N
{"status":"ok","microtimestamp":1787172560.000702}
1787172486.106456100

That machine is 73.9 seconds behind the service. It sounds harmless until a time-window check refuses a token that has not expired yet, or accepts one that has, and the logs on both sides look correct because each machine is consistent with itself. Exactly that drift, a little over a minute, caused real trouble in this project before anyone thought to compare the two clocks. A health poll that also records the delta would have named the problem on the first check.

Health versus ping

The two endpoints answer different questions. Ping replies with a fixed pong: it proves a process accepted the connection and wrote a reply, which is all you want from the cheapest possible reachability probe. It says nothing about whether that process can do any work.

Health is the endpoint to poll when the question is whether the service is fit to serve requests rather than merely listening. Use ping when you are testing a network path or warming a connection, and health when a monitor, a status page or a deployment is about to make a decision based on the answer.

Common uses

Uptime monitor URL

Point the check at the endpoint and assert on status being ok, not just on HTTP 200.

Status page source

Drive a public component indicator from a single field instead of scraping a page.

Readiness gate

Hold a deployment at the traffic cutover until the new target answers with a healthy status.

Drift detection

Log the gap between the server clock and yours on every poll and alert when it grows past a second.

Agent preflight

Let a language model confirm the service is up before it starts a long batch of calls.

Limits and polling interval

The service-wide limit is 5000 requests per IP per 24 hours, and health polls count against it exactly like any other call.

Pick an interval that stays well inside that budget. A check every minute uses 1440 a day, leaving plenty of room for real work from the same address. Every 30 seconds uses 2880, which fits but crowds out everything else. Every 10 seconds is 8640 and will start returning rate limit errors before the day is out, turning the monitor itself into the source of the alarm.
