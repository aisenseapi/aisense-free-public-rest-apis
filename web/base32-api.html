Base32 API

Bytes in, uppercase letters and digits out. Base32 costs more characters than Base64 but survives anything that changes the case of your text: DNS labels, case-insensitive filesystems, printed codes and words read down a phone line.

  • No API key
  • A-Z and 2-7 only
  • Case-insensitive
  • Encode and decode

Encode and decode

POST/base32_encode

POST/base32_decode

https://aisenseapi.com/services/v1

Encode and decode

curl -X POST https://aisenseapi.com/services/v1/base32_encode \
  -H "Content-Type: application/json" \
  -d '{"data":"Hello world"}'
{"base32_encoded_data":"JBSWY3DPEB3W64TMMQ======"}

Send that string back to /base32_decode and the original bytes come out as the response body:

curl -X POST https://aisenseapi.com/services/v1/base32_decode \
  -H "Content-Type: application/json" \
  -d '{"data":"JBSWY3DPEB3W64TMMQ======"}'
Hello world

Input is treated as bytes, so UTF-8 text round-trips unchanged. Blåbær encodes to IJWMHJLCYOTHE=== and decodes back to the same eight UTF-8 bytes.

Request and response

EndpointSends backDescription
/base32_encodebase32_encoded_dataJSON string of A-Z, 2-7 and trailing = padding. The request body is {"data": "..."}; a plain text body works too and is encoded as sent.
/base32_decodeRaw bytesThe decoded bytes as application/octet-stream, which is why the example above prints straight to the terminal. Invalid input returns HTTP 400 with {"error":"Invalid Base32 input."} instead.

Decoding is byte-oriented rather than text-oriented, so binary payloads such as a key, a small image or a compressed blob come back intact. Redirect the response to a file when the decoded bytes are not printable.

Why the output looks like that

  1. Five bytes become eight characters

    Base32 slices the input into 5-bit groups and maps each group to one of 32 symbols: the letters A to Z and the digits 2 to 7. That is the RFC 4648 alphabet. Eight characters carry five bytes, so the encoded form is 60 percent longer than the input. Base64 packs 6 bits per character and grows by only about 33 percent, so Base32 is the bulkier of the two by a clear margin.

  2. Padding fills the last block

    Encoded output always arrives in blocks of eight characters, with = filling any shortfall. In the example above, 11 bytes of input produce 18 characters of payload plus six = signs for a total of 24. The same 11 bytes in Base64 are SGVsbG8gd29ybGQ=, just 16 characters.

  3. Nothing is lost to case folding

    The alphabet contains no lowercase letters, so a system that uppercases or lowercases the string does not damage it. It also leaves out 0, 1, 8 and 9, which removes the classic 0 against O and 1 against I confusion when a human reads a code out or types it in. That is what you are buying with the extra characters.

Common uses

Reading TOTP secrets

Two-factor secrets in otpauth:// enrollment URIs are conventionally Base32 for exactly this reason: users retype them by hand and paste them into apps that may not preserve case. Decode a test secret here to check how many bytes it really carries.

DNS labels

Resolvers and caches are free to change the case of a hostname, so binary data smuggled into a label has to be case-insensitive. Base32 fits inside the letters-and-digits rule for labels; Base64 does not.

Case-insensitive filesystems

On Windows and default macOS volumes, two Base64 names that differ only in case collide as the same file. Base32 filenames cannot collide that way.

Codes people say out loud

Voucher codes, device pairing strings and support reference numbers get dictated over the phone and copied off printouts. An alphabet with no 0, 1, 8 or 9 and no case distinction cuts down the retries.

What counts as valid input

The decoder is forgiving about presentation and strict about the alphabet. Lowercase and mixed case are accepted, and so is missing or short padding, so all of JBSWY3DPEB3W64TMMQ======, jbswy3dpeb3w64tmmq and JBSWY3DPEB3W64TMMQ== decode to the same eleven bytes.

A character outside the alphabet fails the whole request. JBSWY3DPEB3W64TMM0====== ends in a zero, which Base32 has no symbol for, and returns HTTP 400:

{"error":"Invalid Base32 input."}

Check for that status before treating the body as data. There is no partial decode.

Privacy and limits

Base32 is a representation, not protection. Anyone holding the string can decode it. Never send a live two-factor secret, key or credential to a public endpoint - encode those in your own process.

Payloads travel in the POST body rather than the URL, so they stay out of request paths. The service-wide limit is 5000 requests per IP per 24 hours, with no key and no account.
