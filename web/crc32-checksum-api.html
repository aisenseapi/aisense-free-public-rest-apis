CRC32 Checksum API

Send text, get a CRC32 checksum back as a plain unsigned 32-bit integer. It is the cheap, fast way to ask whether two copies of something are still byte-for-byte the same, and to notice when a transfer quietly damaged them.

  • No API key
  • Unsigned 32-bit integer
  • Error detection, not security
  • One POST request

Checksum some data

POST/crc32_checksum

https://aisenseapi.com/services/v1/crc32_checksum

Checksum a string

curl -X POST https://aisenseapi.com/services/v1/crc32_checksum \
  -H "Content-Type: application/json" \
  -d '{"data":"Hello world"}'
{"crc32_checksum":2346098258}

One flipped bit changes the whole value. Capitalising the w gives a completely unrelated number, which is exactly the property that makes a checksum useful:

curl -X POST https://aisenseapi.com/services/v1/crc32_checksum \
  -H "Content-Type: application/json" \
  -d '{"data":"Hello World"}'
{"crc32_checksum":1243066710}

A request with nothing to checksum is refused rather than answered with the checksum of an empty string:

curl -X POST https://aisenseapi.com/services/v1/crc32_checksum \
  -H "Content-Type: application/json" \
  -d '{}'
{"error":"No data to hash or invalid input."}

Response fields

FieldTypeDescription
crc32_checksumintegerThe CRC32 of the UTF-8 bytes of data, as an unsigned 32-bit integer between 0 and 4294967295. Not a hex string, not zero-padded, no prefix.
errorstringReturned instead of the checksum when data is missing or not usable input.

The value is an integer, and that matters

Most confusion with CRC32 comes from presentation rather than arithmetic. This endpoint returns 2346098258 for the string above. A command line tool or a ZIP inspector is likely to print the same checksum as 8bd69e52, because CRC32 is traditionally displayed in hexadecimal. Those are the same number written two ways.

The second trap is signedness. CRC32 fills all 32 bits, so any language that only has signed 32-bit integers reports values above 2147483647 as negative. Java's CRC32 class and .NET both hand back the raw bits, and a naive cast turns this checksum into -1948869038. That is still the same checksum: add 4294967296 to a negative result, or mask with 0xFFFFFFFF, and you are back to the number this API returns.

So when you compare a checksum from here against one produced somewhere else, normalise both sides to an unsigned integer and compare numerically. Do not compare strings. String comparison fails on all three of the differences above at once: base, sign, and leading zeros. A checksum that happens to be small, say 0x0004a3f1, prints as eight hex characters in one tool and as the six-digit decimal 303601 here, and no amount of trimming makes those two strings match.

  1. Take the bytes

    The data string is checksummed as UTF-8 bytes. Non-ASCII characters therefore contribute more than one byte each, and the same visible text encoded differently will produce a different checksum.

  2. Run the standard polynomial

    This is the usual CRC-32 used by ZIP, PNG and gzip, so a value computed here matches what those formats and their tooling compute for the same bytes.

  3. Return the unsigned value

    The result is emitted as a JSON number in the range 0 to 4294967295. Convert to hex yourself if a hex form is what your other system expects.

A checksum is not a hash

The job of a checksum is to detect accidents. Bits flip in memory, a transfer gets truncated, a disk returns a stale sector, a copy script drops the last chunk. Recompute a CRC32 over what arrived, compare it against what the sender had, and mismatches jump out immediately. It costs almost nothing to compute and it fits in four bytes, which is why it is embedded directly in the ZIP file format, in every PNG chunk and in Ethernet frames rather than kept in a separate manifest.

What CRC32 does not do is resist a person. It is a linear function, and given any input it is easy to construct a different input with the same checksum. Anyone who can change the data can change it in a way that keeps the checksum identical, and the check will happily pass.

Never use CRC32 anywhere an attacker might want to fool you: not for passwords, not for signatures or tokens, not to verify a download against tampering, not as a security identifier. Collisions are trivial to construct on purpose. For those jobs use SHA-256, and for a non-adversarial fingerprint that is wider than 32 bits use MD5.

The practical dividing line: CRC32 answers "did this get damaged", a cryptographic hash answers "did somebody change this". Also keep the birthday problem in mind. With only 32 bits, a random pair of unrelated inputs collides roughly once in four billion, so across a set of about 100000 items you should expect around one accidental collision. That is fine for spotting corruption in a single known file, and not fine as a primary key across a large corpus.

Common uses

Transfer verification

Checksum a payload before sending and again after it lands. A mismatch means the file did not survive the trip intact.

Cheap change detection

Compare two copies of a record or config without diffing them. Same number, almost certainly unchanged; different number, definitely changed.

Container integrity fields

Populate or cross-check the CRC32 fields that ZIP entries and PNG chunks carry, using the same standard polynomial.

Deduplication gate

Screen incoming payloads before expensive work. Identical checksums point at duplicates worth a byte comparison, different ones rule duplication out instantly.

Privacy and limits

The data travels in the POST body, not the URL, so it does not appear in request paths.

The service-wide limit is 5000 requests per IP per 24 hours. No account and no API key.
