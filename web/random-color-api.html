Random - Color

Random Color API

One GET request returns one random colour as a hex triplet. Always six digits, always lowercase, always with a leading hash, so the value drops straight into CSS, an SVG fill or a chart config with no formatting step in between.

  • No API key
  • Always six digits
  • Uniform 24-bit
  • One GET request

Get a colour

GET/random_color

https://aisenseapi.com/services/v1/random_color

Get a random colour

curl https://aisenseapi.com/services/v1/random_color
{"random_color":"#e378dc"}

No parameters, no body, no headers to set. Every call is independent and returns a fresh value.

Response fields

FieldTypeDescription
random_colorstringA hex colour in the form #rrggbb: a leading hash followed by exactly six lowercase hexadecimal digits. Total length is always 7 characters.

What the format guarantees

  1. Six digits, never three

    Some generators shorten #ffcc00 to the equivalent three-digit form #fc0. That shortcut breaks naive string handling: slicing characters 1 to 3 for the red channel, comparing two colours for equality, or storing values in a fixed-width column all go wrong the moment a short form appears. This endpoint never emits one. Every response is the full six-digit triplet, so value.slice(1, 3), value.slice(3, 5) and value.slice(5, 7) are always the red, green and blue bytes.

  2. Lowercase and hashed

    Digits a to f are always lowercase and the hash is always present. You can use the string as a dictionary key or compare two values with a plain equality check without normalising case or prefixing anything first.

  3. Uniform across the whole 24-bit space

    Each of the 16777216 possible colours is equally likely. That is genuine randomness rather than a curated palette, so results can land anywhere: near-black, near-white, muddy low-saturation greys and eye-watering saturated primaries are all on the table.

Working with uniform randomness

Uniform means unfiltered. If you need every colour in a set to stay readable against a known background, do not assume the endpoint will avoid the extremes for you - it will not, and over enough calls it will hand you white on white.

Two practical approaches. Filter by luminance on your side: parse the three bytes, compute relative luminance, and reject values above or below your thresholds before using them. Or generate several and choose: request three or four colours and keep the one furthest from your background. Both are a few lines of code and both keep the guarantee that the colour itself was chosen without bias.

Consecutive calls are independent draws, so two requests can return the same colour or two colours that look nearly identical. If you are colouring a set of items that must be visually distinct, deduplicate and check distance between the values yourself.

Common uses

Placeholder avatars

Give every new user or identicon a background colour before they upload a picture.

Chart series colours

Fill a plot config when the number of series is not known ahead of time and no fixed palette covers it.

Design mockups

Seed a wireframe or a component gallery with real colour values instead of grey boxes.

Dashboard log streams

Assign each agent, worker or log source its own tint so lines are easy to tell apart at a glance.

Visual test data

Generate colour inputs for snapshot tests, theme pickers and CSS validation without hardcoding a list.

Privacy and limits

The endpoint takes no input, so there is nothing of yours to log beyond the request itself. No API key and no account are needed. The service-wide limit is 5000 requests per IP per 24 hours, which is plenty for interactive use but worth noting if you plan to colour thousands of rows: fetch once and vary the value locally, or batch your work.
