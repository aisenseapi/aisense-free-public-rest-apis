Time - Conversion

Timestamp Converter API

One endpoint, both directions. Send a Unix timestamp and you get the calendar forms back; send a date string and you get the timestamp. The service decides which it received by looking at the value, and every response carries all of the representations at once, so a caller never needs a second request or a date library of its own.

  • No API key
  • Both directions
  • Format detected
  • One POST request

Convert a time

POST/timestamp_convert

https://aisenseapi.com/services/v1/timestamp_convert

Convert a date string

curl -X POST https://aisenseapi.com/services/v1/timestamp_convert \
  -H "Content-Type: application/json" \
  -d '{"data":"2026-08-19T20:28:10+00:00"}'
{"input":"2026-08-19T20:28:10+00:00","detected":"datetime","timestamp":1787171290,"datetime":"2026-08-19T20:28:10+00:00","rfc2822":"Wed, 19 Aug 2026 20:28:10 +0000","utc_datetime":"2026-08-19T20:28:10+00:00"}

Now the other direction. Send the number instead of the string and the same instant comes back, with detected reporting how the value was read:

curl -X POST https://aisenseapi.com/services/v1/timestamp_convert \
  -H "Content-Type: application/json" \
  -d '{"data": 1787171290}'
{"input":1787171290,"detected":"unix","timestamp":1787171290,"datetime":"2026-08-19T20:28:10+00:00","rfc2822":"Wed, 19 Aug 2026 20:28:10 +0000","utc_datetime":"2026-08-19T20:28:10+00:00"}

There is no direction flag and no separate parse and format endpoint. The two calls above are the same call with a different value in data.

Response fields

FieldTypeDescription
inputstring or numberThe value you sent, echoed back unchanged. It makes the response self-describing in a log: the line shows what was asked as well as what was answered.
detectedstringHow the input was read: unix, unix_ms, datetime or now. This is the field to check when a result looks wrong.
timestampintegerWhole seconds since the Unix epoch, midnight UTC on 1 January 1970. Fractions are dropped, not rounded up.
datetimestringISO 8601 with an explicit offset. UTC unless you asked for an offset.
rfc2822stringThe format email headers and HTTP dates use, for example Wed, 19 Aug 2026 20:28:10 +0000.
utc_datetimestringThe same instant normalised to UTC. Always +00:00, whatever went in and whatever offset you asked for.

All five outputs describe one instant. If datetime and utc_datetime differ, only the wall-clock presentation differs, never the moment.

How the input is detected

The endpoint takes a single data value and has to work out what kind of value it is. There is no format parameter, so the detection rules are worth knowing.

  1. Numbers are epoch seconds

    A number, or a string of digits such as "1787171290", is read as Unix seconds and reported as unix. Thirteen digits and up are read as milliseconds instead and reported as unix_ms, which is what JavaScript's Date.now() produces. The millisecond value is divided down, so timestamp is still whole seconds.

  2. Everything else is parsed as a date

    ISO 8601, RFC 2822 and plain calendar dates all parse and report datetime. A date with no time component becomes midnight, and a datetime with no offset is taken as UTC rather than as the server's local zone.

  3. The literal string now

    Sending "now" converts the server's current clock reading and reports now. It saves a round trip when you want the present moment in all five formats at once.

  4. Anything unparseable is refused

    Input the parser cannot make sense of returns HTTP 400 with {"error":"Unrecognized datetime format. Send a unix timestamp, an ISO 8601 or RFC 2822 datetime, or \"now\"."} rather than guessing. An empty request body returns 400 in the same shape.

The rule that surprises people is the seconds and milliseconds split. A ten-digit number and a thirteen-digit number look alike in a config file and are three orders of magnitude apart in meaning, and a millisecond value read as seconds lands tens of thousands of years in the future. That is exactly the case detected exists for: when a converted date is absurd, read detected before you suspect the conversion.

Asking for a local offset

By default the calendar fields come back in UTC. Add an offset field, written as four digits with an optional leading sign, to render them at a fixed offset instead:

curl -X POST https://aisenseapi.com/services/v1/timestamp_convert \
  -H "Content-Type: application/json" \
  -d '{"data": 1787171290, "offset": "0200"}'
{"input":1787171290,"detected":"unix","timestamp":1787171290,"datetime":"2026-08-19T22:28:10+02:00","rfc2822":"Wed, 19 Aug 2026 22:28:10 +0200","utc_datetime":"2026-08-19T20:28:10+00:00"}

Only datetime and rfc2822 move. The timestamp and utc_datetime fields describe the instant and are unaffected, which is what makes the response safe to log and compare across callers who asked for different offsets. A value that is not a usable offset returns an error rather than quietly falling back.

Note that this is a fixed shift, not a timezone. It has no knowledge of daylight saving, so 0200 is Oslo in summer and wrong in winter. If you need a named zone, resolve it with the Timezones API and pass the offset that comes back.

Common uses

Reading a timestamp out of a log

A log line or a database column holds a bare ten-digit number. Post it and get a readable date back without opening a console or trusting a mental conversion.

Date headers

Take rfc2822 straight from the response for an email Date header or an HTTP date field, in the exact form those specifications expect.

Normalising mixed sources

Feeds from several systems arrive as epoch seconds, epoch milliseconds and half a dozen date strings. Push each one through and store timestamp and utc_datetime, so everything downstream sees one shape.

Agents without date code

Let a language model or an automation convert a time by making one request, instead of generating date arithmetic that is hard to review and easy to get wrong.

Sanity-checking a stored value

Before trusting a date field, convert it and compare detected against what you expected the column to contain. Milliseconds stored in a seconds column show up immediately.

Privacy and limits

The value travels in the POST body, not the URL, so it does not appear in request paths. The conversion is arithmetic on the value you sent and depends on nothing else about the caller.

Conversions are deterministic, so a result for a fixed input and offset is safe to cache indefinitely. The one exception is "now", which reads the server clock and must never be cached. The service-wide limit is 5000 requests per IP per 24 hours.
