Transform - Tokens

JWT API

Sign a set of claims into a JSON Web Token with HS256, and read the claims back out of one. Two endpoints, one shared secret, no account. Built for learning how tokens work, for debugging the ones you already have, and for minting throwaway tokens in test environments.

  • No API key
  • HS256
  • Encode and decode
  • Stateless

Sign or read a token

POST/jwt_encode

POST/jwt_decode

https://aisenseapi.com/services/v1

Encode, then decode

Send the claims you want signed in data and the shared secret in secret. The response carries the finished token in a single field.

curl -X POST https://aisenseapi.com/services/v1/jwt_encode \
  -H "Content-Type: application/json" \
  -d '{"data":{"user":"alice"},"secret":"your_secret_key"}'
{"jwt":"eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJ1c2VyIjoiYWxpY2UifQ.vD5nf5S8f8zwk4JnH8hLwU_RH1HcXbixoFUax8V2SAw"}

HS256 is symmetric, so the same secret that signed the token verifies it. Feed the token straight back to the decode endpoint:

curl -X POST https://aisenseapi.com/services/v1/jwt_decode \
  -H "Content-Type: application/json" \
  -d '{"data":"eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJ1c2VyIjoiYWxpY2UifQ.vD5nf5S8f8zwk4JnH8hLwU_RH1HcXbixoFUax8V2SAw","secret":"your_secret_key"}'
{"decoded_payload":{"user":"alice"}}

Nothing is added to your claims on the way through. The service does not inject iat, exp, jti or an issuer of its own, so the same claims and the same secret always produce a byte-identical token. That determinism is what makes the endpoint useful as a reference to diff your own library against.

What a JWT actually is

A JWT is three base64url segments joined by dots. Split the token above on the dots and you get its three parts.

  1. Header

    eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9 decodes to {"typ":"JWT","alg":"HS256"}. It names the token type and the signing algorithm. This service always writes HS256 and does not accept an algorithm override, so there is no alg: none foot gun here.

  2. Payload

    eyJ1c2VyIjoiYWxpY2UifQ decodes to {"user":"alice"}. These are your claims, verbatim. Base64url is a transport encoding, not a cipher: the padding is stripped and the alphabet swaps +/ for -_ so the value survives a URL, and that is all it does.

  3. Signature

    vD5nf5S8f8zwk4JnH8hLwU_RH1HcXbixoFUax8V2SAw is an HMAC-SHA256 over the first two segments, keyed with your secret, then base64url encoded. It proves the header and payload were not altered by anyone without the secret. It does not hide them.

You do not need the secret, or this endpoint, to read the claims. Any base64 decoder will do it, which you can prove with a second AI SENSE endpoint and no credentials at all:

curl -X POST https://aisenseapi.com/services/v1/base64_decode \
  -H "Content-Type: application/json" \
  -d '{"data":"eyJ1c2VyIjoiYWxpY2UifQ"}'
{"user":"alice"}

A JWT payload is encoded, not encrypted. Anyone who holds the token can read every claim inside it without the secret, exactly as the request above demonstrates. Never put a password, an API key, a card number, a health record or any other confidential value in a payload. And never send a production signing secret to this or to any other public API: a signing key that has left your own infrastructure can no longer prove anything, and every token it ever signed has to be treated as forgeable. Use this service to learn, to debug, to inspect tokens you already hold, and to sign non-sensitive tokens in test environments. Sign your real tokens locally, in your own process, with a secret that never leaves it.

Four ways to send the input

Both endpoints read the same set of input shapes, so you can call them from a shell, a browser form or a file pipeline without reshaping your data first.

1. JSON body, claims as an object. The form shown in the quick start. Best when you build the claims programmatically.

2. JSON body, claims as a string containing JSON. Useful when the claims arrive already serialised and you would otherwise have to parse them only to re-serialise them. Both forms produce the identical token:

curl -X POST https://aisenseapi.com/services/v1/jwt_encode \
  -H "Content-Type: application/json" \
  -d '{"data":"{\"user\":\"alice\"}","secret":"your_secret_key"}'
{"jwt":"eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJ1c2VyIjoiYWxpY2UifQ.vD5nf5S8f8zwk4JnH8hLwU_RH1HcXbixoFUax8V2SAw"}

A string that does not parse as JSON is rejected rather than signed as a bare string, so a serialisation bug upstream surfaces as an HTTP 400 instead of a valid token with a useless payload.

3. Plain text with an X-Secret header. Send the claims as the raw body and keep the secret out of it. On the decode endpoint the raw body is the token itself, which is convenient when you are piping a token out of a log line.

curl -X POST https://aisenseapi.com/services/v1/jwt_encode \
  -H "Content-Type: text/plain" \
  -H "X-Secret: your_secret_key" \
  --data '{"user":"alice"}'
{"jwt":"eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJ1c2VyIjoiYWxpY2UifQ.vD5nf5S8f8zwk4JnH8hLwU_RH1HcXbixoFUax8V2SAw"}

4. File upload in the jwt_data field. A multipart form post, for when the claims already live in a file.

curl -X POST https://aisenseapi.com/services/v1/jwt_encode \
  -F "jwt_data=@claims.json" \
  -F "secret=your_secret_key"
{"jwt":"eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJ1c2VyIjoiYWxpY2UifQ.vD5nf5S8f8zwk4JnH8hLwU_RH1HcXbixoFUax8V2SAw"}

Response fields

FieldTypeDescription
jwtstringReturned by /jwt_encode. The complete token: three base64url segments joined by dots, signed with HS256.
decoded_payloadobjectReturned by /jwt_decode. The claims from the payload segment, after the signature has been verified against the secret you supplied.
errorstringReturned with HTTP 400 when the input cannot be used. See the cases below.

Three input errors are worth knowing about. Encoding with a data string that is not parseable JSON returns {"error":"Invalid data provided. Send a JSON object, or a string containing JSON."}. Encoding without a secret returns {"error":"Secret key is required for encoding."}. Sending an empty body to either endpoint returns {"error":"No data to process or invalid input."}.

Decoding is verification, not just parsing. A token whose signature does not match the secret you supply does not come back as a decoded_payload, and neither does a token carrying an exp claim that has already passed. If you only want to look at the claims of a token you cannot verify, decode its middle segment with the Base64 API instead.

Common uses

Reading a token from a log

An Authorization header turns up in a trace and you need to know which subject, scope or expiry it carries. Paste it in and read the claims back instead of squinting at base64.

Cross-checking a signing library

Sign the same claims with the same secret here and in your own code, then compare the two strings. Because nothing is auto-injected, any difference is a real difference in your header, your claim ordering or your HMAC.

Test fixtures

Mint tokens with fabricated user ids and scopes for integration tests and API mocks, using a throwaway secret your test suite also knows.

Teaching how JWTs work

Encode a token, decode its payload with a plain base64 call, and the class sees for themselves that a signature protects integrity rather than confidentiality.

Privacy and limits

Claims, tokens and secrets travel in the POST body rather than the URL, so they do not land in request paths. That is a reason to prefer the body, not a reason to trust the endpoint with anything real. Treat every value you send to a public API as disclosed.

The endpoints are stateless: there is no token store, no lookup by identifier and no endpoint that lists what was encoded earlier. The service-wide limit is 5000 requests per IP per 24 hours.
