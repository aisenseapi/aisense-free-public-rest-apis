Hash - Verification

Hash Verify API

Send the original data, the digest you expect and the algorithm name. The service hashes the data and compares the result against your value in constant time, then tells you both what algorithm it used and what digest it actually computed.

  • No API key
  • Constant-time compare
  • MD5, SHA1, SHA256, SHA512
  • One POST request

Verify a digest

POST/hash_verify

https://aisenseapi.com/services/v1/hash_verify

Check data against a digest

curl -X POST https://aisenseapi.com/services/v1/hash_verify \
  -H "Content-Type: application/json" \
  -d '{"data":"Hello world","hash":"3e25960a79dbc69b674cd4ec67a72c62","algorithm":"md5"}'
{"match":true,"algorithm":"md5","computed":"3e25960a79dbc69b674cd4ec67a72c62"}

All three request fields are required. data is the original content, hash is the digest you are checking against, and algorithm names the function that produced it.

Response fields

FieldTypeDescription
matchbooleanTrue when the digest computed from data equals the hash you sent. The comparison is constant time.
algorithmstringThe algorithm actually used, echoed back so a caller that built the request dynamically can confirm it asked for what it thinks it asked for.
computedstringThe digest the service derived from your data. On a mismatch this is the useful half of the answer: you learn what the value really was instead of only that it was wrong.

Why the comparison is constant time

Comparing two digests looks like a one-line problem, and that is exactly why it goes wrong so often. The obvious way to do it is a plain string equality check, and a plain string equality check is written to be fast: it walks the two strings and returns the moment it finds a byte that differs. A value whose first character is wrong is rejected sooner than a value whose first twenty characters are right.

That difference is tiny, but it is real and it is measurable. An attacker who can send many attempts and time each one can guess the first character, keep whichever guess was answered a hair more slowly, then move on to the second, and walk a secret digest out of the service one character at a time. Instead of brute forcing the whole value, the work becomes linear in its length. This is the classic timing side channel, and it is not exotic: it shows up in signature checks, token comparisons and download verifiers written by careful people in a hurry.

  1. Hash the data

    The service computes the digest of data using the algorithm you named.

  2. Compare every byte

    The computed digest and your hash are compared with a routine that always inspects the whole value and accumulates the differences, rather than returning at the first one it finds.

  3. Answer at a fixed cost

    A wrong first character costs the same as a wrong last character, so the response time carries no information about how close a guess was. There is nothing to measure.

Use this endpoint whenever the digest you compare against is a secret, such as a webhook signature or an authentication token. For a public checksum published next to a download, the timing does not matter, but the endpoint costs you nothing either way.

Supported algorithms

ValueDigest lengthNotes
md532 hex charactersStill everywhere in file checksums and legacy integrations. Broken for collision resistance, so treat it as a transfer error check, not a security guarantee.
sha140 hex charactersCommon in older signature schemes and version control. Also collision broken, and kept here for compatibility with systems that publish SHA1 digests.
sha25664 hex charactersThe sensible default for anything new: release checksums, webhook signatures, integrity records.
sha512128 hex charactersWider digest from the same family. Useful when a counterpart already specifies it.

Common uses

Downloaded file check

Compare a file you fetched against the digest the publisher put on their release page before you trust or unpack it.

Webhook signatures

Verify the signature on an incoming payload without hand rolling the comparison, which is the exact place a naive equality check leaks timing.

Archive integrity

Confirm a backup or archive still hashes to the value recorded when it was written, so silent corruption or tampering shows up.

Agent-side verification

Let a language model or automation confirm that data it received matches an expected digest, without giving it any hashing code of its own to get wrong.

Privacy and limits

The data and the digest travel in the POST body, not the URL, so neither ends up in a request path or a server access log line.

No account and no API key. The service-wide limit is 5000 requests per IP per 24 hours.
