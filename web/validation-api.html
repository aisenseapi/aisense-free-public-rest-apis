Web utility - Validation

Validation API

Check a business number by its check digit: IBAN, payment card, Norwegian organisasjonsnummer and kontonummer, and phone number. Pure arithmetic, one POST, no account.

  • No API key
  • Check-digit maths
  • Nothing looked up
  • Norwegian formats

Validate a value

POST/validate/{type}

https://aisenseapi.com/services/v1/validate/iban

Validate an IBAN

curl -X POST https://aisenseapi.com/services/v1/validate/iban \
  -H "Content-Type: application/json" \
  -d '{"data": "NO9386011117947"}'
{ "type": "iban", "valid": true, "normalized": "NO9386011117947",
  "country": "NO", "structure_ok": true, "length_ok": true, "checksum_ok": true }

An invalid value is a result with valid: false and the failing check named, never an error. Everything is arithmetic on our side: valid means well-formed with a correct check digit, not that the account exists.

The five types

TypeChecks
ibanISO 13616 mod-97, with a length table for the countries this service meets. Outside it, length_ok is null and the checksum still decides.
cardLuhn. The card number is never echoed back in the response.
orgnrNorwegian organisasjonsnummer, 9 digits, MOD11. Accepts an NO prefix and an MVA suffix.
kontonummerNorwegian bank account, 11 digits, MOD11.
phoneE.164 shape only. Says nothing about whether the number is in service.

More examples

# Payment card, Luhn
POST /validate/card    {"data": "4111 1111 1111 1111"}  -> { "valid": true, "luhn_ok": true }

# Norwegian org number
POST /validate/orgnr   {"data": "NO 922 601 151 MVA"}   -> { "valid": true, "normalized": "922601151" }

# Norwegian bank account
POST /validate/kontonummer  {"data": "1234.56.78903"}   -> { "valid": true }

# Phone, E.164
POST /validate/phone   {"data": "004740000000"}         -> { "valid": true, "e164": "+4740000000" }

Common uses

Form validation

Catch a mistyped account or card before submitting it downstream.

Agent input checking

Verify a number a model extracted before it is acted on.

Norwegian onboarding

Check an org number or bank account at signup without a register call.

Data cleaning

Flag rows whose check digits do not hold.

Privacy and limits

The value travels in the POST body, not the URL. The card endpoint never reflects the number back in its response, so a real card number does not end up in the caller's logs through us.

The service-wide limit is 5000 requests per IP per 24 hours.
