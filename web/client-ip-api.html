Client IP API

What is my IP address, answered as JSON. One GET request returns the public address this server saw your traffic arrive from, in a single field. Nothing to install, nothing to sign up for.

  • No API key
  • One GET request
  • IPv4 and IPv6
  • One JSON field

Read your public address

GET/client_ip

https://aisenseapi.com/services/v1/client_ip

Ask for your address

curl https://aisenseapi.com/services/v1/client_ip
{"ip":"46.212.190.81"}

That is the whole interface. No body, no parameters, no headers to set. Paste the URL into a browser, run it in a shell, put it in a container entrypoint or drop it into a CI job and read the one field that comes back.

Response fields

FieldTypeDescription
ipstringThe public address the request arrived from, in normal textual form: dotted quad for IPv4, colon separated hexadecimal for IPv6.

What the value actually is

The address in the response is the source address of the connection as this server observed it. That is not necessarily the address of the machine that made the call.

If your traffic passes through a home router, a corporate NAT, a proxy, a VPN or a cloud egress gateway, you get the public address of that last hop, not the address on your own network interface. Every laptop on the same office network normally reports the same value.

That distinction is the single most common misunderstanding about this kind of endpoint, and it is also exactly what makes the endpoint useful. If you connect a VPN and the value changes, the tunnel really is carrying your traffic. If it does not change, the tunnel is down, split tunnelling is routing this destination around it, or something is leaking. The same check works for an egress gateway in front of a cluster: call the endpoint from inside a pod and you learn which public address the outside world will see, which is rarely written down anywhere you can trust.

IPv4 and IPv6

Both families are returned in their usual textual form, and which one you get depends entirely on how the connection was made. A dual stack machine resolves the hostname, finds both an A and an AAAA record, and picks a family before any request is sent. So a host that you think of as having a particular IPv4 address may hand you an IPv6 answer instead.

Treat that as a feature rather than a surprise: it is a quick way to see which family your network actually prefers in practice. Forcing the choice with curl's -4 or -6 flag and comparing the two answers tells you both of your public addresses, which matters when a firewall rule or an allowlist has only ever been written for one of them.

Common uses

VPN and proxy verification

Call it once before connecting and once after. A changed address proves the tunnel is carrying traffic to this destination; an unchanged one proves it is not.

CI runner allowlisting

Add the call as a pipeline step to discover the egress address a build actually leaves from, then allowlist it on a database, a partner API or a staging firewall.

Firewall rule debugging

When a rule that should match refuses to, compare the address the server really sees with the one written in the rule. Mismatches are usually a NAT hop nobody accounted for.

Container egress checks

Run it from inside a container or a pod to confirm which NAT gateway that workload leaves through, without depending on cloud metadata endpoints.

Agent self reporting

Let a language model or an automation report the address it is calling from, with no shell access and no platform specific tooling.

Privacy and limits

The response contains nothing that every server you connect to does not already receive. The endpoint simply shows it back to you.

The service-wide limit is 5000 requests per IP per 24 hours. Because the counter is keyed on the same address the endpoint reports, everyone sharing a NAT or an egress gateway shares one budget, which is worth remembering before putting the call in a tight polling loop.

To turn an address into a hostname, country and timezone, pass it to the IP Reverse Lookup API.
