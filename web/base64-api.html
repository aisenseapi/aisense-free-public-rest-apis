Transform - Encoding

Base64 API

Base64 turns arbitrary bytes into 64 printable characters that survive channels which only carry text. These two endpoints do that conversion both ways, and the decode side lets one Accept header decide whether you get plain text, a typed JSON envelope or the raw bytes as a file.

  • No API key
  • Text, JSON or bytes
  • Binary safe
  • Two endpoints

Encode or decode

POST/base64_encode

The two calls you probably want

Encoding takes your bytes and returns the Base64 string:

curl -X POST https://aisenseapi.com/services/v1/base64_encode \
  -H "Content-Type: application/json" \
  -d '{"data":"Hello world"}'
{"base64_encoded_data":"SGVsbG8gd29ybGQ="}

Decoding back to readable text needs one extra header. Accept: text/plain is what most callers actually want, and it is the mode people most often forget to ask for:

curl -X POST https://aisenseapi.com/services/v1/base64_decode \
  -H "Content-Type: application/json" \
  -H "Accept: text/plain" \
  -d '{"data":"SGVsbG8gd29ybGQ="}'
Hello world

That is the whole happy path. The rest of this page covers the two other decode modes, the shape of the input the endpoints accept, and the alphabet rules that decide whether a string is valid Base64 at all.

What Base64 actually does

Base64 is not compression and it is not encryption. It is a transport format. It reads your input three bytes at a time, splits those 24 bits into four groups of six, and maps each group onto one character from a 64 character alphabet: A-Z, a-z, 0-9, + and /. Because every output character is ordinary printable ASCII, the result travels intact through JSON strings, email bodies, HTTP headers, XML attributes, log lines and copy-paste, all of which would mangle raw bytes.

The cost is size. Three bytes in produce four characters out, so anything you encode grows by roughly a third before padding is counted. That is the trade: you spend about 33 percent more bandwidth and storage to make binary data safe to put somewhere that only understands text.

Encoding: three ways to send the input

A JSON body with a data key encodes the value of that key:

curl -X POST https://aisenseapi.com/services/v1/base64_encode \
  -H "Content-Type: application/json" \
  -d '{"data":"Hello world"}'

{"base64_encoded_data":"SGVsbG8gd29ybGQ="}

A plain text body encodes the body itself, which saves you from escaping quotes and newlines into JSON:

curl -X POST https://aisenseapi.com/services/v1/base64_encode \
  -H "Content-Type: text/plain" \
  --data-binary 'Hello world'

{"base64_encoded_data":"SGVsbG8gd29ybGQ="}

A file goes the same way, sent as the raw request body. The example below uploads an eight byte file containing nothing but the PNG signature:

curl -X POST https://aisenseapi.com/services/v1/base64_encode \
  -H "Content-Type: application/octet-stream" \
  --data-binary @png-header.bin

{"base64_encoded_data":"iVBORw0KGgo="}

The rule behind all three forms: if the body parses as JSON and carries a non-empty data string, that string is encoded. Otherwise the raw request body is encoded byte for byte. That fallback is deliberate, but it means a malformed JSON envelope is never reported as an error. Sending {"data": broken returns {"base64_encoded_data":"eyJkYXRhIjogYnJva2Vu"}, which is Base64 of your broken envelope rather than of the value you meant. Multipart uploads with curl -F land in the same path and encode the multipart wrapper, boundary markers and all, so send files as the raw body instead.

Text is encoded as its UTF-8 bytes, because Base64 is defined over bytes and not over characters. {"data":"Blåbær"} returns {"base64_encoded_data":"QmzDpWLDpnI="}: six characters, eight UTF-8 bytes, twelve Base64 characters.

FieldTypeDescription
base64_encoded_datastringStandard Base64 with = padding. The encode endpoint always answers with Content-Type: application/json; charset=utf-8 and ignores the Accept header.

Decoding returns three different shapes

Decoding produces bytes, and bytes can be anything: a sentence, a JSON document, a gzip stream, half a JPEG. There is no single response format that serves all of those honestly, so /base64_decode looks at your Accept header and picks one of three modes. Callers who send no Accept header and expect text are the most common source of confusion with this endpoint.

1. Accept: text/plain returns the decoded text

curl -X POST https://aisenseapi.com/services/v1/base64_decode \
  -H "Content-Type: application/json" \
  -H "Accept: text/plain" \
  -d '{"data":"SGVsbG8gd29ybGQ="}'

Hello world

The body is the decoded text and nothing else, served as text/plain; charset=utf-8. No envelope, no quoting, no second decode step in your code. Use this whenever you know the payload is text.

2. Accept: application/json returns a typed envelope

If the decoded bytes parse as JSON, you get them back as real JSON, already parsed, under type: json:

curl -X POST https://aisenseapi.com/services/v1/base64_decode \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{"data":"eyJvayI6dHJ1ZX0="}'

{"type":"json","decoded_data":{"ok":true}}

If they do not parse as JSON, the bytes come back still Base64 encoded, labelled so you know it:

curl -X POST https://aisenseapi.com/services/v1/base64_decode \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{"data":"SGVsbG8gd29ybGQ="}'

{"type":"binary","encoding":"base64","decoded_data":"SGVsbG8gd29ybGQ="}

At first glance that looks like a no-op, because decoded_data is byte for byte what you sent. It is not a no-op: the service decoded your input, found the result was not JSON, and re-encoded the same bytes so they could cross the wire without damage. Your client decodes decoded_data locally and holds the exact original bytes.

The reason for the wrapping is that a JSON string is a sequence of Unicode characters, not a sequence of bytes. Arbitrary bytes have no faithful representation inside one. Anything that tried would have to guess a character encoding, and every byte that is not valid in that encoding would be dropped or replaced by a substitution character, silently corrupting the payload before it ever reached you. The service refuses to guess. It tells you the truth with type and encoding and leaves the final decoding to code that knows what the bytes are. This is also why a client should always branch on type rather than assume decoded_data is readable.

3. No Accept header returns the raw bytes as a download

With no Accept header, with */*, or with application/octet-stream, the response body is the decoded bytes themselves:

curl -X POST https://aisenseapi.com/services/v1/base64_decode \
  -H "Content-Type: application/json" \
  -d '{"data":"SGVsbG8gd29ybGQ="}' \
  -D - -o decoded.bin

HTTP/2 200
server: AISENSE
content-type: application/octet-stream
content-disposition: attachment; filename="decoded_data.bin"
content-length: 11

This is the mode to use for files. Add -o output.bin in curl and the bytes land on disk unchanged; a browser follows the Content-Disposition header and saves them as decoded_data.bin. Round trips are exact, so an image encoded through /base64_encode and sent straight back through /base64_decode is byte identical to the original.

Accept header sentResponse
text/plaintext/plain; charset=utf-8, decoded text as the whole body
application/jsonapplication/json with type, optional encoding and decoded_data
application/octet-stream, */* or no headerapplication/octet-stream as an attachment named decoded_data.bin
anything elseHTTP 406

Accept lists are scanned left to right and the first supported type wins, so Accept: text/plain, */* gives you text while Accept: application/xml, */* falls through to the download. A browser default of text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8 also ends in a download, because */* is the first entry the service recognises. Only a list with no supported entry at all, such as a bare Accept: text/html, is rejected.

Padding, alphabet and URL safety

This endpoint speaks standard Base64 as defined in RFC 4648 section 4, not the URL-safe variant. The last two alphabet characters are + and /, and padding is =. A base64url string that uses - and _ instead is rejected: sending Pz8_Pw== returns HTTP 400 with {"error":"Invalid Base64 input."}. Translate - to + and _ to / before you send it. Going the other way, remember that a standard Base64 string is not safe to drop into a URL unescaped, because +, / and = all have meaning there and need percent-encoding.

Padding exists because the encoder works in three byte groups. When the input length is not a multiple of three, the final group is short and = characters mark how much was missing, which is what lets a decoder recover the exact original length:

"a"     becomes  "YQ=="
"ab"    becomes  "YWI="
"abc"   becomes  "YWJj"
"abcd"  becomes  "YWJjZA=="

The encoder always emits that padding. The decoder is more forgiving than the specification requires: SGVsbG8gd29ybGQ without its trailing = still decodes to Hello world, and whitespace inside the input is ignored, so Base64 that was wrapped at 64 columns by a tool like openssl base64 can be posted with its line breaks intact. Characters outside the alphabet are the one thing that is not tolerated.

400{"error":"Invalid Base64 input."}The decode input contains characters outside the standard alphabet, or the body could not be read as Base64 at all. A JSON body with no usable data key, such as {}, lands here too, because the raw body is then tried as Base64 and fails.
400{"error":"No data to decode or invalid input."}/base64_decode was called with no body.

406{"error":"Unsupported Accept header.","accept":"application\/xml","allowed":["application\/json","text\/plain","application\/octet-stream","*\/*"]}The Accept header listed no type the decode endpoint can produce. The accept field echoes what you sent and allowed lists the four accepted values.

Encoding has no equivalent of invalid input: every sequence of bytes is encodable, so the only failure mode is sending nothing at all.

Common uses

Inline assets as data URIs

Encode a small icon or font from the command line and paste the string after data:image/png;base64, to embed it in a stylesheet or a single file HTML page.

Read an opaque blob from a log

A webhook payload or queue message arrives as an unreadable string. One POST with Accept: text/plain tells you what it says, without pasting it into an unknown website.

Carry binary through a text-only pipeline

Message queues, CSV columns, YAML config and JSON APIs all reject raw bytes. Encode on the way in, decode with Accept: application/octet-stream on the way out, and the bytes survive unchanged.

Build test fixtures for Basic auth

Basic auth sends user:password as Base64. Generate the header value for a throwaway test account here, and keep real production credentials off any public endpoint.

Give an agent a decoder

A language model with HTTP access can decode a Base64 string it encountered in a document or tool result with a single call, instead of needing a code sandbox for it.

Privacy and limits

Base64 is an encoding, not a cipher. Anyone holding the string can read the contents, so it hides nothing. Do not send production secrets, tokens or personal data to a public endpoint just to encode them; that conversion is a few lines of code in every language and belongs on your own machine.

Payloads travel in the POST body rather than the URL, so they do not appear in request paths. There is no account and no API key, and the service-wide limit is 5000 requests per IP per 24 hours.
