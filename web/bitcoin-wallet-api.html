Crypto - Bitcoin

Bitcoin Wallet API

Two GET requests. One generates a legacy Bitcoin key pair for testing and teaching. The other reads the confirmed balance of any address on the public chain, in BTC and in satoshis. The generated keys are made on a server and travel over the network, so they are test material only.

  • No API key
  • Two endpoints
  • BTC and sats
  • Test keys only

Generate a key pair

GET/bitcoin/generate_new_wallet

https://aisenseapi.com/services/v1/bitcoin/generate_new_wallet

Read this before you generate anything

The key pair is generated on a remote server and sent back to you over the network. That means it is not yours alone. Never put real funds in an address generated this way.

This is not a caveat about a hypothetical attacker. A private key that was created somewhere other than your own machine, and then transmitted, has existed in at least one process memory and one network path you do not control. There is no way to un-know a secret. Treat every key from this endpoint as public from the moment it is created.

What it is genuinely good for: learning how a private key, its WIF encoding and a public address relate to each other; building and testing wallet-handling code without touching real value; generating throwaway addresses for test suites and documentation examples; and demonstrating address formats to someone who has never seen one.

For real funds, use a hardware wallet or well-audited local software that generates keys offline, on a device you control, and never transmits the secret anywhere.

The balance endpoint carries none of this risk. It is read-only and takes only an address, which is public information by design, so it is safe to call for any address including your own.

Generate a key pair

curl https://aisenseapi.com/services/v1/bitcoin/generate_new_wallet

The response has exactly three fields. The values below are placeholders written to show the shape of each field. They are not a real key pair and no real generated key is published on this page.

{
  "private_key": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "private_key_wif": "5PLACEHOLDERPLACEHOLDERPLACEHOLDERPLACEHOLDERPLACEH",
  "public_address": "1PLACEHOLDERPLACEHOLDERPLACEHOLD"
}
FieldTypeDescription
private_keystringThe raw key as 64 hexadecimal characters, which is 32 bytes. This is the entire secret.
private_key_wifstringThe same key in Wallet Import Format, the base58 encoding that wallet software accepts on import.
public_addressstringThe legacy address derived from the key. Begins with the digit 1.

Check a balance

GET/bitcoin/balance/{address}

The address goes in the path. The example below uses the genesis block address, the first Bitcoin address that ever existed, which makes a stable and well-known example to test against.

curl https://aisenseapi.com/services/v1/bitcoin/balance/1A1zP1eP5QGefi2DMPTfTL5SLmv7DivfNa
{"wallet":"1A1zP1eP5QGefi2DMPTfTL5SLmv7DivfNa","final_balance_btc":107.36782465,"final_balance_sats":10736782465}
FieldTypeDescription
walletstringThe address you asked about, echoed back so a response can be matched to its request when several are in flight.
final_balance_btcnumberConfirmed balance expressed in BTC.
final_balance_satsnumberThe same balance in satoshis, the integer base unit. 1 BTC is 100000000 sats.

Both units are returned so nobody has to divide by 100000000 and nobody has to guess which unit they were handed. Use final_balance_sats for anything that adds, compares or stores a balance: it is a whole number and stays exact. final_balance_btc is a decimal number in JSON, and once a JSON parser turns it into a double it is subject to the usual binary floating point rounding. It is for display, not for arithmetic.

Balances change. The number above was correct when this page was written and the genesis address in particular keeps receiving small tribute payments, so treat any figure in documentation, including this one, as a snapshot rather than a constant to assert in a test.

How the three values relate

  1. The private key is the whole secret

    32 random bytes, shown as 64 hex characters. Everything else on this page is derived from it. Whoever holds it controls whatever the address holds, which is exactly why a key that arrived over a network is a teaching aid and not a wallet.

  2. WIF is the same key, packaged

    Wallet Import Format is not a second key. It is the same 32 bytes wrapped in base58 with a version byte and a checksum so that a mistyped character is caught instead of silently importing the wrong key. It is the form most wallet software expects when you paste a key in.

  3. The address is a one-way derivation

    The public address comes from the key through hashing and cannot be run backwards to recover it. That asymmetry is why an address is safe to publish, put in a QR code, or hand to the balance endpoint, while the key never is.

One format limit worth knowing before you build against this: the generator produces legacy P2PKH addresses, the kind beginning with 1. It does not produce bech32 segwit addresses beginning with bc1, and it does not produce taproot addresses. If the code you are testing must handle bc1 input, this endpoint will not exercise that path.

Common uses

Test suite fixtures

Give integration tests a fresh throwaway address each run instead of committing a real one to the repository.

Wallet code under test

Exercise parsing, validation, checksum handling and display of keys and addresses against real format, zero value.

Teaching key material

Show a class or a colleague, in one request, how a private key, its WIF encoding and a public address are three views of one thing.

Watch-only balance checks

Poll public addresses for confirmed balances in a dashboard or an alert, using the integer sats field for the arithmetic.

Documentation examples

Produce address strings for screenshots, API samples and README files without borrowing somebody else's real address.

Privacy and limits

Generated keys are transmitted over the network and must never hold real funds. Balance lookups are read-only and expose nothing that is not already on the public chain.

The address in a balance request travels in the URL path, so it will appear in request logs along the way. For a public chain address that is not a secret, but it does link an IP to an interest in that address, which is worth knowing if you are polling an address you care about.

The service-wide limit is 5000 requests per IP per 24 hours, with no API key and no account. Balances only move when a block confirms, so cache a result for a few minutes rather than polling in a tight loop, and you will never come close to the ceiling.
