Crypto - Ethereum

Ethereum Wallet API

Two GET requests, no account and no node to run. One mints a throwaway Ethereum key pair for testing, the other reads the mainnet balance of any address in both wei and ether. The generated pair is for test code and documentation only, never for money.

  • No API key
  • Test keys only
  • Wei and ether
  • Two GET requests

Generate or look up

GET/ethereum/generate_new_wallet

GET/ethereum/balance/{address}

https://aisenseapi.com/services/v1

A key from this endpoint is not a secret

Never send real funds to an address generated here. The private key is created on a remote server and travels back to you across the internet. A private key that has left the machine it was born on is no longer secret, whatever the transport encryption. Treat every pair this endpoint returns as public knowledge, and assume anything sent to that address can be taken.

What the generator is genuinely good for: learning what a key pair actually looks like, exercising wallet and address-handling code, and producing throwaway addresses for test fixtures, seed data, screenshots and documentation. Nothing in that list involves value, and that is the point.

For an address that will hold real funds, generate the key where it never touches a network service: a hardware wallet, or audited local software running offline. Then verify the address on the device screen rather than trusting whatever a piece of software prints.

The balance endpoint is a different matter. It only reads public chain data, so it is safe to call for any address, including addresses you control and addresses you do not.

Generate a key pair

curl https://aisenseapi.com/services/v1/ethereum/generate_new_wallet
{
  "private_key": "PLACEHOLDER - 64 hex characters, no 0x prefix",
  "public_address": "PLACEHOLDER - 0x followed by 40 hex characters"
}

The two values above are placeholders, not a real pair. A live call returns a freshly generated secp256k1 private key and the address derived from it, and every call returns a different one. There is no seed phrase, no derivation path and no way to recover the pair once you drop the response.

Look up a balance

The address goes in the path. Both endpoints are plain GET requests, so a browser address bar works as well as curl.

curl https://aisenseapi.com/services/v1/ethereum/balance/0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045
{
  "wallet": "0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045",
  "balance_eth": "6.635339380601433797",
  "balance_wei": "6635339380601433797"
}

That is the balance of a well-known Ethereum mainnet address at the time this page was written; a live call returns whatever it holds now. The lookup is read-only and needs no key, so it works as a drop-in replacement for a node RPC call when all you want is a balance.

Response fields

Generate

FieldTypeDescription
private_keystringThe 32-byte secp256k1 private key as 64 hex characters, with no 0x prefix. Test use only, as explained above.
public_addressstringThe address derived from that key: 0x followed by 40 hex characters. The letters come back mixed case, but the casing is not a valid EIP-55 checksum.

Balance

FieldTypeDescription
walletstringThe address exactly as it appeared in the request path, casing included.
balance_ethstringBalance in ether, always written with 18 decimal places. A string, not a number.
balance_weistringBalance in wei, the base unit. A string, and normally far larger than a JavaScript number can hold exactly.

Both balance values are strings

This is the single most common way to get a wrong number out of this endpoint, so it is worth being precise about. One ether is 1000000000000000000 wei, and balances are reported to the last wei. A JavaScript number is an IEEE-754 double, which represents integers exactly only up to 9007199254740991. The balance above, 6635339380601433797 wei, is nine orders of magnitude past that limit.

Parse it with Number() or parseFloat() and you get 6635339380601434112, which is 315 wei more than the real balance. No exception, no warning, just a quietly wrong figure that survives every later calculation. The ether field is no safer: 6.635339380601433797 carries 18 decimal places, a double holds roughly 17 significant digits, and parseFloat hands back 6.635339380601434 with the tail of the balance simply gone.

So keep both fields as strings from the response all the way to storage. When you need arithmetic, load balance_wei into an arbitrary-precision integer type: BigInt in JavaScript, the built-in int in Python, BigInteger in Java, math/big in Go, or a fixed-point decimal column rather than a float in your database. Divide down to ether only at the moment of display, and do that division on the integer rather than on a float.

Other places this bites

  1. The mixed case is not an EIP-55 checksum

    An address such as the one in the balance example is checksummed, but the addresses this generator returns are not: the letter casing does not encode a valid EIP-55 checksum. Libraries that validate it, including getAddress in ethers.js, will reject the value outright. Lowercase public_address before you hand it over and let the library apply its own checksum.

  2. A malformed address returns 404, not a validation error

    The balance route only matches 0x followed by exactly 40 hex characters. One character short, or an ENS name instead of an address, and the request falls through to the generic Unknown endpoint error with HTTP 404. Do not read that 404 as "this address does not exist on chain": an address holding nothing at all still answers with HTTP 200.

  3. An empty wallet is not an empty string

    An address with no ether returns balance_wei as "0" and balance_eth as "0.000000000000000000". Because the ether field is always padded to 18 decimals, comparing it against "0" reports a non-empty wallet even when the wallet is empty. Test balance_wei instead.

  4. The echoed address is not canonical

    The lookup accepts the address in upper, lower or mixed case and echoes back exactly what you sent, so wallet is a copy of your input rather than a normalised form. Normalise addresses yourself before using them as cache or database keys, or the same wallet will occupy several rows.

What people build with this

Test fixtures

Fill unit tests, seed data and staging databases with addresses that look real without going near a funded wallet.

Wallet code practice

Feed generated pairs through your address validation, checksum and storage code to see how it behaves before real keys arrive.

Docs and screenshots

Publish example addresses in documentation and demos where there is nothing to steal even if the page runs for years.

Read-only balance panels

Show the ether held by a treasury, donation or contract address in a dashboard or bot without running a node or holding an RPC key.

Privacy and limits

The key pair is created on our server and returned in the response body. Whatever the server does or does not keep, you cannot verify that from the outside, which is precisely why the pair is only ever safe for testing.

The address you look up is part of the request path, so it appears in access logs. Ethereum addresses and their balances are public chain data, so nothing secret leaks, but the log does connect an IP address to an interest in a particular wallet. The service-wide limit is 5000 requests per IP per 24 hours.
