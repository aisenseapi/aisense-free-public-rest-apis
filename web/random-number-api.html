Random - Numbers

Random Number API

One GET request returns a random integer inside the bounds you asked for. The reply also repeats the range it drew from, so the caller can verify the bounds the service actually used instead of trusting that its own URL was read the way it intended.

  • No API key
  • Plain GET
  • Inclusive bounds
  • Range echoed back

Draw a number

GET/random_number/{from}/{to}

https://aisenseapi.com/services/v1/random_number/1/100

Draw a number

curl https://aisenseapi.com/services/v1/random_number/1/100
{"random_number":59,"range":{"from":1,"to":100}}

There is no body, no header and no key to send, so the same call works from a browser address bar, a shell, a spreadsheet formula or a language model tool call. Both bounds are inclusive: /random_number/1/100 can return 1 and can return 100.

Range in the path

The range is optional and is expressed as path segments rather than query parameters. How many segments you supply decides how the range is read.

RequestRange usedNotes
/random_number1 through 6The default is a single die.
/random_number/101 through 10A single segment is the upper bound. The lower bound stays at 1.
/random_number/1/1001 through 100Two segments are from and to.
/random_number/-5/5-5 through 5Negative bounds are accepted on either side of zero.
/random_number/50/5050 through 50A range of one value always returns that value.
curl https://aisenseapi.com/services/v1/random_number

{"random_number":4,"range":{"from":1,"to":6}}
curl https://aisenseapi.com/services/v1/random_number/-5/5

{"random_number":3,"range":{"from":-5,"to":5}}

Response fields

FieldTypeDescription
random_numberintegerThe drawn value, always between range.from and range.to inclusive.
rangeobjectThe bounds the draw was made from, after defaults were filled in and the two bounds were ordered.
range.fromintegerLower bound, inclusive.
range.tointegerUpper bound, inclusive.

Echoing the range is a deliberate design detail rather than padding. A URL built by string concatenation is easy to get wrong: a variable comes through empty, a template drops a segment, a value arrives as a float and loses its tail. Because the reply states the bounds it used, a caller can assert on range in the same step where it reads random_number, and a wrong range fails loudly instead of quietly producing plausible numbers from a range nobody asked for.

How the path is read

  1. Count the segments

    Zero segments means 1 through 6. One segment is the upper bound with a lower bound of 1. Two segments are the lower and upper bound in that order.

  2. Order the bounds

    Reversed bounds are sorted rather than refused, so a swapped pair still produces a usable draw. Sending /random_number/100/1 answers with {"random_number":7,"range":{"from":1,"to":100}}, and the echoed range is what tells you the swap happened.

  3. Reject what is not a number

    A segment that is not an integer does not fall back to a default. /random_number/abc/10 returns HTTP 404 with {"error":"Unknown endpoint. See https:\/\/www.aisense.no\/free-public-apis for the reference."}, so a broken URL cannot be mistaken for a successful draw.

Wide ranges behave the same way as narrow ones. /random_number/1/1000000 returned {"random_number":626730,"range":{"from":1,"to":1000000}}.

Common uses

Sampling for review

Pull a random row index out of a known record count when a person needs to spot check output rather than read all of it.

Retry and load-test jitter

Ask for a delay in milliseconds so retrying clients spread out instead of firing again in lockstep after an outage.

Test fixtures

Vary quantities, ages and prices in smoke tests so a suite is not silently passing on one hard-coded value.

Decisions an agent cannot bias

A language model asked to pick a number leans on its own priors. An external draw settles tie-breaks, bucket assignment and turn order without that pull.

Demo prize draws

Pick a winner live from a numbered list in a workshop or stream, with the echoed range visible as proof of the bounds.

Limits and suitability

This is a number that crossed the network. It is not suitable for anything security sensitive: not tokens, not keys, not passwords, not lottery draws, not anything an adversary benefits from predicting. Use a local cryptographic random source for those, such as the secure random facility built into your language or operating system.

What it is good for is everything where the requirement is variety rather than secrecy: sampling, test fixtures, load-test jitter, retry backoff, demo draws and giving an autonomous agent a decision it cannot influence. The service-wide limit is 5000 requests per IP per 24 hours, so a tight loop that needs thousands of values per second should draw locally and use this endpoint for a seed or a one-off choice instead.
