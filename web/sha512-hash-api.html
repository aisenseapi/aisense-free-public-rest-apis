Hash - SHA-2

SHA-512 Hash API

SHA-512 is the wide member of the SHA-2 family: the same design as SHA-256, but built on 64-bit words and producing a 512-bit digest written as 128 lowercase hex characters. Send a JSON string, a plain text body or a file upload and get that digest back in one request.

  • No API key
  • 128 hex characters
  • JSON, text or file
  • Constant-time verify

Hash a string

POST/sha512_hash

https://aisenseapi.com/services/v1/sha512_hash

Hash a string

curl -X POST https://aisenseapi.com/services/v1/sha512_hash \
  -H "Content-Type: application/json" \
  -d '{"data":"Hello world"}'
{"sha512_hash":"b7f783baed8297f0db917462184ff4f08e69c2d5e5f79a942600f9725f58ce1f29c18139bf80b06c0fff2bdd34738452ecf40c488c22a7e3d80cdf6f9c1c0d47"}

That digest is a constant. Any correct SHA-512 implementation, in any language, on any machine, returns those same 128 characters for the eleven bytes Hello world, which is what lets two systems that never talk to each other agree on whether they hold identical content.

Three input styles are accepted and all three hash the same bytes to the same digest. A JSON body with a data field, as above. A raw body sent as plain text, which saves you escaping quotes and newlines into JSON:

curl -X POST https://aisenseapi.com/services/v1/sha512_hash \
  -H "Content-Type: text/plain" \
  --data-binary "Hello world"
{"sha512_hash":"b7f783baed8297f0db917462184ff4f08e69c2d5e5f79a942600f9725f58ce1f29c18139bf80b06c0fff2bdd34738452ecf40c488c22a7e3d80cdf6f9c1c0d47"}

Or a file posted as multipart/form-data, in which case the file bytes are hashed and the form wrapper is not:

curl -X POST https://aisenseapi.com/services/v1/sha512_hash \
  -F "file=@hw.txt"
{"sha512_hash":"b7f783baed8297f0db917462184ff4f08e69c2d5e5f79a942600f9725f58ce1f29c18139bf80b06c0fff2bdd34738452ecf40c488c22a7e3d80cdf6f9c1c0d47"}

The file above contains exactly the eleven bytes of Hello world with no trailing newline. That detail matters more than people expect: a shell echo appends a newline, so hashing a file written with echo gives a completely different digest from hashing the same visible text without it. When a checksum disagrees and the content looks identical, a trailing newline is the first thing to rule out.

Response fields

FieldTypeDescription
sha512_hashstringExactly 128 characters, lowercase hex, 64 bytes of digest, the same length whether the input was one byte or one gigabyte. An empty input still returns a valid digest, so a well-formed response is not evidence that you sent the payload you intended.

Input is treated as bytes. Text is hashed as UTF-8, so accented characters and emoji contribute their encoded bytes rather than any code point abstraction. A local implementation that encodes the same string as UTF-16 or Latin-1 produces a different digest, and encoding is the second thing to check after trailing whitespace when two systems disagree.

SHA-512 compared with SHA-256

Both are SHA-2. They share a structure, a security lineage and a standard, and neither has a practical break. The differences that matter in day to day work are narrower than the name gap suggests.

Digest length. SHA-512 returns 128 hex characters against 64 for SHA-256. Twice the storage per fingerprint, twice the width in a log line or a manifest column. For most integrity work SHA-256 already has collision headroom nobody will exhaust, so length alone is rarely the deciding argument.

Speed. This is the part that surprises people: on 64-bit hardware SHA-512 is frequently faster per byte than SHA-256. SHA-512 operates on 64-bit words and processes 128-byte blocks, while SHA-256 operates on 32-bit words and 64-byte blocks, so a 64-bit CPU moves twice the data per round with the same register width. The picture flips on 32-bit microcontrollers, and it flips again on modern x86 and ARM chips with SHA-256 instructions built into the silicon, where hardware acceleration puts SHA-256 back in front. Measure on the hardware you will actually run on before treating either as the fast option.

When the longer digest earns its place. Long-term archival integrity, where a manifest is meant to outlive the assumptions behind it and the extra bits are cheap insurance. And compliance with a standard or protocol that names 512 bits outright, in which case the choice was made for you and this endpoint just has to match it.

Otherwise SHA-256 remains the interoperability default and is what most tooling, package registries and release checksums expect. Pick SHA-512 for a reason, not for the bigger number. Note also that truncating this endpoint's output to 64 characters does not give you SHA-512/256: that variant is a distinct algorithm with different initial hash values, and its digests will not match a truncated SHA-512.

Compare against an expected digest

POST /hash_verify takes data and an expected hash and reports whether they match. The algorithm is inferred from the length of the hash you supply, so a 128-character hex string is read as SHA-512 and a 64-character one as SHA-256.

curl -X POST https://aisenseapi.com/services/v1/hash_verify \
  -H "Content-Type: application/json" \
  -d '{"data":"Hello world","hash":"b7f783baed8297f0db917462184ff4f08e69c2d5e5f79a942600f9725f58ce1f29c18139bf80b06c0fff2bdd34738452ecf40c488c22a7e3d80cdf6f9c1c0d47"}'
{"match":true,"algorithm":"sha512","computed":"b7f783baed8297f0db917462184ff4f08e69c2d5e5f79a942600f9725f58ce1f29c18139bf80b06c0fff2bdd34738452ecf40c488c22a7e3d80cdf6f9c1c0d47"}

The comparison is constant-time, so the response takes the same time whether the first character differs or only the last. An ordinary string equality that exits at the first mismatched character leaks, through timing, how much of a guessed digest was correct. The computed value is returned on a mismatch as well, which shows you what the input actually hashes to instead of leaving you with a bare false.

Not for passwords

Do not store passwords as SHA-512 digests. SHA-512 is designed to be fast, and fast is the wrong property for password storage: commodity hardware computes it at enormous rates, so a stolen table of digests falls to a dictionary attack quickly. Use a deliberately slow key derivation function instead - bcrypt, scrypt or Argon2 - each of which is built with a tunable work factor and per-password salting.

The longer digest changes nothing here. Length protects against collisions, not against guessing, and password cracking is guessing. Adding your own salt to SHA-512 defeats precomputed tables but leaves raw guessing speed untouched, which is the part that decides the outcome. The same caution applies to SHA-256, MD5 and every other fast hash.

Common uses

Archival manifests

Write a digest next to every file in a long-lived archive. Years later a re-hash tells you which objects survived intact and which were corrupted by a failing disk or a bad migration, without needing a second copy to diff against.

Standard-mandated digests

Some specifications, signature profiles and procurement rules name SHA-512 explicitly rather than leaving the hash open. When that is the requirement, this endpoint produces the exact value the reviewer will check.

Large file checksums

On 64-bit servers without SHA-256 hardware instructions, SHA-512 often finishes a multi-gigabyte file sooner. Use it to fingerprint release artifacts, backups and disk images where throughput is the constraint.

Cross-implementation debugging

When your library and someone else's disagree, hash the same input here and see which side matches. A neutral third implementation turns an argument about code into a question about encoding or trailing bytes.

Content addressing

Key an object store or cache by digest so identical bytes always land on the same key and duplicate uploads collapse. The wider digest gives generous headroom for stores intended to grow without bound.

Privacy and limits

The input travels in the POST body, not the URL, so it does not appear in request paths. Even so, a hash is not encryption, and the plaintext reaches this service before it is hashed. SHA-512 is one call in every standard library, so keep genuinely confidential input inside your own process and use this endpoint for testing, tooling and content you are comfortable sending.

The service-wide limit is 5000 requests per IP per 24 hours. No API key and no account are required.
