Product note - 3 October 2026

Time Zones by Name, and a Home for WorldTimeAPI's Paths

Most of what this API answers is the time. Of the 303 575 calls counted on 2 October, 96 percent asked for a timestamp or a date. Two additions today are for the programs behind those calls: /datetime takes a zone by name, which follows summer time where a fixed offset cannot, and WorldTimeAPI's paths and fifteen fields answer at aisenseapi.com/api for every client that service left behind.

The time endpoints are called by software that was set up once and then left to run. In fourteen minutes this morning a Delphi application asked for /timestamp 1 212 times, clients that identify as the game ARK asked for /microtimestamp 175 times, Godot games asked for /datetime with a fixed offset 113 times, and ESP32 boards and okhttp clients came in between. Nobody changes code like that every season, which is the problem with a fixed offset.

A fixed offset is wrong for half the year

/datetime/+0200 is Oslo in summer. From 01:00 UTC on 25 October 2026, when Europe goes back to standard time, it is Oslo plus an hour, and it stays wrong until someone edits the offset. A zone name does not have that problem, because the zone carries its own rules:

GET /services/v1/datetime/Europe/Oslo
{"datetime":"2026-10-03T11:12:16+02:00","timezone":"Europe/Oslo","abbreviation":"CEST","utc_offset":"+02:00","dst":true,"unixtime":1791018736}

Any IANA name works, in any case, including three-part names such as America/Argentina/Buenos_Aires. The answer by name says what the offset is right now and whether summer time is on, since that is the reason to ask by name. An unknown name is a 400 with a fix rather than a quiet UTC, because a wrong hour that looks right is the exact failure this is meant to remove.

The offset forms are unchanged. About 29 000 calls a day, with an offset or without one, expect {"datetime": ...} and nothing else, and that is what they keep getting. +02:00 with a colon is now accepted beside +0200, and an hour-only value such as /datetime/1 is still not a route.

WorldTimeAPI's paths, at a new host

WorldTimeAPI was the clock in a great many ESP32 sketches, Arduino projects, games and scripts. It no longer answers: on 3 October 2026 every connection to worldtimeapi.org was reset, over HTTP and HTTPS, and from a second network as well. Its paths and its fifteen fields answer here, so a client moves by changing the start of the URL and nothing else.

BeforeAfter
http://worldtimeapi.org/api/timezone/Europe/Oslohttps://aisenseapi.com/api/timezone/Europe/Oslo
http://worldtimeapi.org/api/iphttps://aisenseapi.com/api/ip
http://worldtimeapi.org/api/timezone.txthttps://aisenseapi.com/api/timezone.txt

The fields are WorldTimeAPI's, with its names, types and order: the local and UTC time with microseconds, the offset in force, the standard offset, whether summer time is on and when the current period began and ends, the day of the week and of the year, the ISO week, the Unix time and the caller's address. The .txt form gives one key: value per line, and the errors use its words, unknown location Europe/Pari, with our fix beside them. /api/ip finds the zone of the caller's address in GeoLite2-City and caches it for an hour, so a board that asks every minute costs one lookup an hour.

The one change you cannot skip

HTTPS only.

This host does not serve plain HTTP. An ESP32 sketch that used http://worldtimeapi.org with a WiFiClient moves to https:// and a WiFiClientSecure; client.setInsecure() is enough to read a clock. The WorldTimeAPI alternative page has the five lines and every field.

The answers took 150 to 244 ms there and back, over a fresh TLS connection every time, which is almost all of it network. Not every public address has a zone in the database: 1.1.1.1 answered 404 rather than a guess, and asking by zone name is the way around that.

Where it sits

The datetime page and the time guide have zones by name, the WorldTimeAPI alternative page has the paths, the fields and the ESP32 change, and the Python and JavaScript clients and the OpenAI tool definitions in the public repository have the new calls. The free MCP server's get_current_time already took a zone name and is unchanged. Every path counts towards the 5000 calls per address per day like the rest of the API.

Take one

Change the host, keep the code.

No account, no key, and the same fifteen fields your sketch already parses.
