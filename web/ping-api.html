Web - Liveness

Ping API

The smallest endpoint on the service. No parameters, no work performed, no database or upstream touched - just a fixed two-field JSON body. That is the whole point: a request that cannot fail for any reason other than the network or the service being unreachable, so a failure means exactly one thing.

  • No API key
  • Fixed response
  • No dependencies
  • One GET request

Ping the service

GET/ping

https://aisenseapi.com/services/v1/ping

Ping the service

curl https://aisenseapi.com/services/v1/ping
{"ping":"pong"}

Fifteen bytes, every time. There is no query string to get wrong and no body to send. The response carries access-control-allow-origin: *, so it works from browser JavaScript, and cache-control: no-store, so a proxy cannot hand you a stale success from a service that has since gone down.

Response fields

FieldTypeDescription
pingstringAlways the literal pong. It is a constant, not a computed value, so nothing about it varies by time, caller or load.

Check the HTTP status first and the body second. A 200 with {"ping":"pong"} means a request reached the service and the service answered. Anything else - a timeout, a DNS failure, a TLS error, a 502 from something in front of the service - is a network or availability problem, because there is no application logic here that could produce an error of its own.

Ping is not a health check

These two endpoints answer different questions and the difference matters when you are wiring up monitoring.

  1. Ping answers: is anything answering on this address

    It proves the DNS record resolves, the TLS handshake completes, the routing works and a process is listening and returning HTTP. It proves nothing beyond that.

  2. Health answers: are the parts working

    The health check API reports on the service's actual state. Use it when you need to know whether the service can do its job, not merely whether it exists.

  3. Pick by what you will do with the answer

    Reachability, latency measurement and connectivity smoke tests want ping, because a fixed response keeps the measurement clean. Deciding whether to send real traffic wants health. A load balancer pointed at ping will happily keep routing to a process that is up but broken.

Measuring round-trip latency

Because the server does no work, the elapsed time is very close to pure network cost plus TLS. That makes ping a fair yardstick for comparing one location against another. Ask curl for the timing and throw the body away:

curl -s -o /dev/null -w "%{http_code} in %{time_total}s\n" \
  https://aisenseapi.com/services/v1/ping
200 in 0.176645s

The first call to a host includes DNS resolution and a full TLS handshake, so it is always the slowest. Run it three or four times and read the later numbers if you want steady-state latency rather than cold-start cost.

Common uses

Latency from a location

Time the round trip from a region, an office or a CI runner to compare network paths with a constant-size response.

CI connectivity gate

Run one ping before an integration suite. If it fails, the runner has no outbound internet and the suite would only produce confusing failures.

NAT keepalive

A client behind NAT or a corporate firewall can poll at a low rate to keep its outbound path from being reaped by an idle timeout.

First thing to try when something breaks

When another call misbehaves, ping separates "the network is broken" from "that specific endpoint is broken" in one command.

Agent internet check

An autonomous agent can call ping to confirm it actually has working outbound access before it reports that a remote resource is unavailable.

Limits and polling

Ping is unauthenticated, and it counts against the service-wide limit of 5000 requests per IP per 24 hours exactly like every other endpoint. It is not free of quota just because it is cheap to serve.

That budget is the one real way to get this endpoint wrong. A monitor polling once per second would issue 86400 requests in a day and burn through the allowance in under an hour, taking the rest of your integration down with it. A sustained rate of one request per 17 seconds is the ceiling. Poll every 30 or 60 seconds instead: 1440 requests a day still detects an outage quickly and leaves most of the quota for real work.

Remember the limit is per IP, so everything sharing an office NAT or a CI egress address shares one bucket. If you need to know your own outbound address, the client IP API will tell you which one the quota is being counted against.
