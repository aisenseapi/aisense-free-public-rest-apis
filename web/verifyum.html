How it works

The browser does the sensitive work.

The browser creates the private proof data and gives it back to you. Verifyum receives no original file bytes, filename, raw file hash, nonce or private manifest.

  1. Select a file

    The file is opened by browser code on your device.

  2. Create the private manifest

    SHA-256, file size and a random nonce are combined in a versioned manifest.

  3. Compute the commitment

    The browser canonicalizes the manifest and derives a public commitment from it.

  4. Download the private draft

    You keep the draft with the original file. It is not uploaded.

  5. Anchor the commitment

    Only the domain-separated commitment is submitted for a finalized Solana transaction.

  6. Save the public proof

    Keep the public link. You can also download a QR-code PNG or print an A4 PDF receipt.

For AI agents

Connect directly with one MCP URL.

Verifyum also offers a stateless MCP endpoint for AI agents. Connect with one URL and no account, wallet, payment, API key or npm package. File hashing, nonce generation and private-manifest construction stay on the agent's machine.

claude mcp add --transport http verifyum https://api.verifyum.com/mcp

The endpoint exposes three tools for anchoring a completed commitment, reading a public proof and checking a public proof. The verification tool performs the Ed25519 signature check in the web runtime and returns the exact Solana RPC request for a separate confirmation.

The official MCP registry lists com.verifyum/mcp version 0.1.0. MCP is an additional access method. The browser flow, public HTTP API and published protocol remain available.

Read the agent guide.

Agent decision records

An agent can assemble one local record from its system instructions, exact prompt, model and version, parameters, tool calls and output, then anchor only the commitment. A matching proof shows that the record existed unchanged by the block time. It does not prove that the agent actually ran with the recorded settings.

For normal use, anchor one record per case or day, or the head of a local hash chain. Do not anchor every individual decision.

Witness Layer

One checkpoint, several public witnesses.

Finalized proofs are grouped into hourly and daily Merkle checkpoints. OpenTimestamps with eventual Bitcoin anchoring, a public GitHub checkpoint log, the Internet Archive, Certificate Transparency, a qualified EU timestamp under eIDAS, Software Heritage and a witness-cosigned Sigsum log add supplemental records around the primary Solana proof and Verifyum signature - nine evidence records in total.

Aggregate privacy

External witnesses receive one aggregate checkpoint root. They never receive the file, raw file hash, nonce, private manifest or proof ID.

Public inspection

Checkpoint documents, Merkle membership and channel receipts are available through read-only public URLs. Membership shows inclusion in a checkpoint. The separate receipt shows whether an external channel confirmed it.

Visible state

Each channel reports pending, confirmed, unavailable or failed. Bitcoin confirmation takes time by design.

Same proof boundary

A pending or missing witness does not invalidate the Solana proof. The number of channels is not a quality score.

What to keep

Keep the private draft and the public proof.

The current flow gives you a private draft before anchoring and a separate public proof after finalization. Keep the original file and private draft together, and save the public proof link.

QR code

The QR code contains only the already-public proof URL. The image is generated by the free AISenseAPI QR endpoint.

PDF receipt

The proof page builds an A4 receipt from public metadata. Your browser renders it for printing or saving as PDF.

Public access

No account, wallet or payment.

A hard ceiling allows at most 10 new anchor reservations per rolling hour per IP. Lower daily, client and global limits may apply when needed to protect the free service.

Clear limits

A file proof answers a narrow question.

A finalized proof shows that a commitment to the exact file bytes existed no later than the estimated Solana block time. It does not decide who created the file or whether its contents are true.

Byte identity

A changed byte produces a different SHA-256 value and a different commitment.

Independent timestamp

The finalized transaction gives a public time boundary that can be checked without relying on the Verifyum database.

No creation-time claim

The block time shows when the commitment existed. It cannot prove when the original file was first created.

No legal or content claim

A matching proof does not establish authorship, ownership, legal signature validity or whether the contents are true.
