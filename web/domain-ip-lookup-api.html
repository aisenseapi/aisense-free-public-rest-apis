Domain IP Lookup API

Put a hostname in the path and get back the IP address it currently points at. One GET request, no body, no key. The answer is what this server's resolver sees right now, which makes it a useful second opinion when your own machine disagrees.

  • No API key
  • One GET request
  • Domain in the path
  • Independent resolver

Resolve a domain

GET/domain_ip_lookup/{domain}

https://aisenseapi.com/services/v1/domain_ip_lookup/example.com

Resolve a hostname

curl https://aisenseapi.com/services/v1/domain_ip_lookup/example.com
{"domain":"example.com","ip":"104.20.23.154"}

The domain goes in the path, not in a query string or a body. There is nothing else to send.

Response fields

FieldTypeDescription
domainstringThe hostname that was looked up, echoed back so a response can be matched to its request.
ipstringThe address this server's resolver returned for that hostname at the moment of the request.

What the answer actually means

A DNS lookup is not a lookup in a single global table. It is a question asked of one resolver, from one place, at one moment, and all three of those change the answer. This is where people misread the result, so it is worth being precise about what the ip field is and is not.

  1. Answers differ by resolver

    Different resolvers hold different cached copies of a record and expire them on their own schedule. Two resolvers queried a second apart can hand back different addresses for the same name, and neither is wrong.

  2. Answers differ by location

    Large sites sit behind CDNs and anycast networks that deliberately return a nearby edge address. The value you get here is the edge closest to this server, not an origin machine and not the address a visitor in another country would receive.

  3. Records change

    An A record can be edited at any time, and the change spreads outward as caches expire rather than switching everywhere at once. What you get is a snapshot from this server's resolver at this moment, not a permanent fact about the domain.

Read that way, the endpoint is most valuable precisely because it is a second opinion. Comparing the address it returns with what your own machine resolves is the fastest way to tell a real DNS problem apart from a local one: a stale entry in your operating system or browser cache, a hosts-file line you added months ago and forgot, or a record you changed that simply has not reached your resolver yet. If the two agree, the change is live. If they differ, the difference itself is the diagnosis.

For the opposite direction, taking an address and asking what is known about it, see the IP Reverse Lookup API.

Common uses

Confirm a DNS change went live

Point a domain somewhere new, then poll from outside your own network to see when the record actually changed.

Verify a migration

After moving a site or service, check that the hostname now resolves to the new host rather than the retired one.

Catch a stale local cache

When a site loads wrongly only for you, compare this answer with your machine's and you will know within seconds whether the fault is local.

Allowlist an address

Resolve a partner hostname to the address a firewall rule or security group needs.

Resolution without a shell

Let an agent or a browser-based tool resolve a hostname over HTTP when it has no access to dig or nslookup.

Privacy and limits

The hostname appears in the request path, so it is visible in ordinary request logs. Treat internal hostnames the same way you would treat any other value you put in a URL.

No account and no API key. The service-wide limit is 5000 requests per IP per 24 hours, which is ample for polling a record through a propagation window as long as you leave a sensible gap between checks.
