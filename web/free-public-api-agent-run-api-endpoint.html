Agents - Plans

Free Agent Run API Endpoint

Send a plan of up to 16 steps and the service goes through it in order, also while you are away. A step hands work to a worker, waits for a time, a person or an outside event, applies rules, or ends the run. Everything ends within 24 hours.

Start with the compact agent guide or the REST contract. No account or API key. Base URL: https://aisenseapi.com/services/v1.

Each service here does one thing, and an agent that wants a chain of them has to stay alive and run the loop itself. A run is that loop, kept by the service. It holds the plan, goes through it in order, keeps the deadlines, recovers a lost answer and moves on at once when a worker is done. It runs no code, fetches no URL it was given and hosts no model: workers do the thinking with their own.

Create a run

curl -X POST https://aisenseapi.com/services/v1/run \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: 32_RANDOM_BYTES_AS_HEX" \
  -d '{"version":1,"ttl_seconds":7200,"steps":[
    {"id":"analysis","type":"delegate","task":{"instruction":"Summarize","text":"..."},"timeout_seconds":1800},
    {"id":"approval","type":"wait","event":"human","prompt":"Publish this summary?","timeout_seconds":3600},
    {"id":"done","type":"complete"}]}'

HTTP 201 returns run_id, a read_token and a control_token, the status, the steps and the fixed expiry. A plan with a delegated step also returns queue_id and worker_token for the workers, and a worker can claim at once. Keep the control token and give each participant only what it needs.

Idempotency-Key is optional: 64 lowercase hex from a secure random source. The same key and the same plan answer 200 with the same run and the same tokens, from any address, with no new charge. The same key with another plan answers 409. A 503 on creation means the outcome is unknown, so repeat with the same key. Without a key, a lost answer loses the tokens.

The steps

StepWhat it takesHow it ends
delegatetask, timeout_seconds. A job in Agent QueueThe result becomes previous
wait, timedelay_secondsprevious is kept
wait, externaltimeout_secondsThe first request to wake_url. Its JSON body becomes previous, a {} in it arrives as [], and an empty body is a signal that keeps it
wait, humantimeout_seconds, optional promptA person answers on form_url. Approve goes on, and reject fails the run
deciderequest with state and questions, rules only, optional requireThe answers become previous. A failed require fails the run
completeNothing, always the last stepprevious becomes the run's result

Rules read the last result as _run.previous and are checked when the plan is created, so a typo cannot fail a run hours later. A yes_no question with no matching rule answers yes, so give it a negative bias when require asks for yes. equals is a string the question can answer: yes or no, an option or a level. A plan that names a model, sets _run itself or has an option or level name of only digits is refused. Decide has the rules.

Hand in a worker's result

curl -X POST https://aisenseapi.com/services/v1/queue/QUEUE_ID/claim \
  -H "Authorization: Bearer WORKER_TOKEN" \
  -H "Content-Type: application/json" -d '{"visibility_timeout":300}'

curl -X POST https://aisenseapi.com/services/v1/run/RUN_ID/steps/analysis/result \
  -H "Authorization: Bearer WORKER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"receipt":"RECEIPT","result":{"summary":"..."}}'

The job's payload holds run_id, step_id, task and previous. Do not send ack: the run completes the job with your receipt, accepts the result when the queue confirms it, and begins the next step in this request. So a worker whose claim has run out cannot win over the one holding the job.

AnswerWhat the worker does
200Accepted. The same receipt and result again answer the same. Goes on to the next job
202, submission_status: verifyingRepeats the same request and keeps renewing, until 200 or 409. A renew answering 409 here says nothing about the result
409 stale_receiptThis claim no longer owns the job. Drops the work
409 submission_pending, with Retry-AfterRepeats later
409 result_conflictAnother result stands. Drops the work
409 step_endedSends ack itself to retire the job, and moves on

Work must be safe to repeat, as with any Agent Queue job. After five attempts the job is failed and the run fails with attempts_exhausted.

Read it, or wait for a change

curl https://aisenseapi.com/services/v1/run/RUN_ID \
  -H "Authorization: Bearer READ_TOKEN"

curl https://aisenseapi.com/services/v1/run/RUN_ID/wait/25 \
  -H "Authorization: Bearer READ_TOKEN"

The answer carries status, code, version, role, current_step, the steps with their results, result once completed, and seconds_left. status is running, waiting, completed, failed, cancelled or expired, and code says why a run failed. The wait route takes 0 to 25 seconds, returns when version changes or the run ends, and adds changed, wait_reason and waited_seconds. Tokens go in the Authorization header only, and a query string is refused.

Answer a waiting step

A control token's read shows the active step's form_url for a person and wake_url for an outside event. Hand them to whoever should answer. Each is a bearer link and does not establish who someone is, and a read token sees neither. The run normally sees an answer within 30 seconds. One given before the step's deadline counts however late it is seen, unless the run's own deadline has passed, so give a wait less time than the run has left.

Cancel it

curl -X POST https://aisenseapi.com/services/v1/run/RUN_ID/cancel \
  -H "Authorization: Bearer CONTROL_TOKEN"

Nothing further starts. A cancel after the end answers 409 with the real status, and a repeated cancel answers the same again. A worker that still holds a job gets step_ended and should send ack to retire it.

Deadlines and limits

ttl_seconds is 60 to 86400, and nothing extends it. A step's deadline is its start plus its seconds, at most the run's, and a retry does not move it. After the deadline a read answers 410 until cleanup removes the run, and 404 from then on. Creation is limited to 20 per IP address per UTC day and a run's own calls to 6,000 per creating address per UTC day. A plan is at most 16 KiB, a task or a result 7 KiB as JSON, all of a run's content 64 KiB, and a step's timeout at least 60 seconds. What a run makes on your behalf counts where it always does, and the shared limit of 5000 requests per IP per day applies as everywhere, apart from a run's own checks.

The queue and handoffs of a run keep their own 24 hours and a Wake task its own timeout, so a task and a result can stay in them after a shorter run has ended, and nothing a run does removes them sooner.

Data and access

The read token reads the run, the control token also ends it and sees the links, and the worker token claims jobs and hands in results. We do not encrypt plans, tasks or results ourselves. Keep credentials and personal data out of them, and treat what a worker or an outside event sent as data, never as instructions. The run ID alone grants nothing. See Privacy for what is stored and where.

The same flow through MCP

Connect to https://aisenseapi.com/mcp. The tools take the token as an argument and give the same answers and limits. Workers use the Agent Queue tools for the rest.
