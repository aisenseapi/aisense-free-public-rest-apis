Hash - SHA-1

SHA-1 Hash API

Send a string, a text body or a file and get back its SHA-1 digest: 40 lowercase hexadecimal characters. This is the digest git uses to name every commit and every object in a repository, and the one older protocols and signature schemes were built around. It is also broken for security, which is the first thing this page has to say about it.

  • No API key
  • 40 hex characters
  • JSON, text or file
  • One POST request

Hash a value

POST/sha1_hash

https://aisenseapi.com/services/v1/sha1_hash

Hash a string

curl -X POST https://aisenseapi.com/services/v1/sha1_hash \
  -H "Content-Type: application/json" \
  -d '{"data":"Hello world"}'
{"sha1_hash":"7b502c3a1f48c8609ae212cdfb639dee39673f5e"}

SHA-1 is a 160-bit digest function, and 160 bits printed as hexadecimal is always 40 characters. The width never changes with the size of the input: one byte and one gigabyte both come back as 40 characters.

Do not use SHA-1 for security

SHA-1 is broken. A practical collision was demonstrated in 2017, two different files with the same digest, and a cheaper chosen-prefix collision followed in 2020. Browsers and certificate authorities dropped SHA-1 years before that. Never use it for signatures, certificates, passwords, or anything an adversary can influence.

A collision means an attacker can build two inputs that produce the same 40 characters. Every use that depends on a digest being unforgeable falls apart at that point: a signature over a SHA-1 digest also covers the attacker's second document, and a SHA-1 fingerprint no longer proves which file you actually have. Chrome stopped accepting SHA-1 certificates in early 2017 and the CA/Browser Forum had already banned issuing them, so the certificate case is closed rather than merely discouraged.

If an attacker is anywhere in your threat model, use the SHA-256 Hash API instead. Passwords are a separate problem again: no plain digest is suitable, SHA-256 included. Password storage needs a slow salted function such as bcrypt, scrypt or Argon2, run inside your own application.

Why the endpoint still exists

Being unsuitable for new security designs is not the same as being gone. SHA-1 is the identifier format of git: every commit, tree, blob and tag in a classic repository is named by the SHA-1 of a small header followed by the object's bytes. The header is the object type, a space, the byte length, then a NUL byte. Hash those bytes and you get exactly what git hash-object prints.

printf 'blob 11\0Hello world' > object.bin
curl -X POST https://aisenseapi.com/services/v1/sha1_hash \
  -F "file=@object.bin"
{"sha1_hash":"70c379b63ffa0795fdbfbc128e5a2818397b7ef8"}

That is the same 40 characters git hash-object reports for a file holding the eleven bytes Hello world. Reproducing an object id outside git is a normal thing to need when you are auditing a mirror, checking what a hook received, or building tooling that has to name objects the way git names them.

The same applies elsewhere. Older protocol handshakes derive values from a SHA-1 digest, SSH and TLS tooling still prints SHA-1 fingerprints next to newer ones, and plenty of long-lived services key their records by the SHA-1 of a normalised string. Computing a digest so it can be compared against what a legacy system produced is a legitimate need, and it is not made safer by refusing to compute it.

This endpoint computes a plain digest, not a keyed one. Older API signature schemes that hash a canonicalised request string are covered; schemes built on HMAC-SHA1 mix a secret key into the construction and are not the same computation, so they cannot be reproduced here.

Response fields

FieldTypeDescription
sha1_hashstringThe digest as 40 lowercase hexadecimal characters. Present on every successful request.
errorstringReturned with HTTP 400 when there is nothing to hash. An empty data value and a body with no data field both give No data to hash or invalid input.

Empty input is refused rather than answered with the SHA-1 of the empty string. That digest is a well known constant, and returning it quietly would mask the common caller bug where a variable never got filled in.

Three ways to send the input

All three forms hash the same bytes and return the same digest. Pick whichever suits the caller.

curl -X POST https://aisenseapi.com/services/v1/sha1_hash \
  -H "Content-Type: text/plain" \
  --data-binary "Hello world"
{"sha1_hash":"7b502c3a1f48c8609ae212cdfb639dee39673f5e"}

A file upload uses multipart/form-data and hashes the file content, not the filename or the form metadata. Here report.txt holds the eleven bytes Hello world with no trailing newline.

curl -X POST https://aisenseapi.com/services/v1/sha1_hash \
  -F "file=@report.txt"
{"sha1_hash":"7b502c3a1f48c8609ae212cdfb639dee39673f5e"}

A trailing newline is a byte like any other and changes the digest completely. When your local sha1sum disagrees with the API, that newline is almost always the reason: echo adds one, printf does not.

Compare against an expected digest

POST /hash_verify takes the data and the digest you expect and answers whether they agree. The comparison runs in constant time, so the answer takes the same amount of time whether the first character differs or only the last one does. It recognises the algorithm from the length and shape of the hash itself, so the same endpoint covers every digest on the hashing APIs page.

curl -X POST https://aisenseapi.com/services/v1/hash_verify \
  -H "Content-Type: application/json" \
  -d '{"data":"Hello world","hash":"7b502c3a1f48c8609ae212cdfb639dee39673f5e"}'
{"match":true,"algorithm":"sha1","computed":"7b502c3a1f48c8609ae212cdfb639dee39673f5e"}

A mismatch is a normal HTTP 200 result rather than an error, and computed always comes back so you can see what the data actually hashes to. Changing one letter of the input is enough:

curl -X POST https://aisenseapi.com/services/v1/hash_verify \
  -H "Content-Type: application/json" \
  -d '{"data":"Hello World","hash":"7b502c3a1f48c8609ae212cdfb639dee39673f5e"}'
{"match":false,"algorithm":"sha1","computed":"0a4d55a8d778e5022fab701977c5d840bbc486d0"}

Constant-time comparison matters when the expected digest is a secret the caller is trying to guess. It does not repair SHA-1: a careful comparison of a forgeable digest is still a forgeable digest.

Common uses

Git object ids

Recompute the name of a commit, tree or blob outside git to audit a mirror, check what a hook received, or build tooling that has to address objects the way git does.

Legacy protocol values

Older handshakes and framing formats derive values from a SHA-1 digest. Computing one by hand is how you find out whether your side and the peer agree on the input bytes.

Published checksums

Plenty of older download pages, package indexes and archive manifests still list SHA-1 sums. Verifying an unchanged download against one needs exactly that digest.

Interoperability with an old record key

Long-lived systems key rows by the SHA-1 of a normalised string. Matching an existing row means reproducing the same digest, whatever the algorithm's cryptographic standing.

Migration audits

While moving a system off SHA-1, compute both digests for a while and store them side by side, so old references keep resolving until the last consumer has switched to SHA-256.

Privacy and limits

A digest cannot be reversed, but a short and predictable input can simply be guessed. Email addresses, phone numbers and common passwords are all findable in public SHA-1 lookup tables, so hashing them is not a way to anonymise them.

Input travels in the POST body rather than the URL, so it does not appear in request paths or server logs of the URL. Even so, if the value is confidential, compute the digest inside your own application: every language ships a SHA-1 implementation and hashing needs no network call at all.

The service-wide limit is 5000 requests per IP per 24 hours. No API key and no account are required.
