SHA-256 Hash API

SHA-256 reduces any input, from a three-letter string to a multi-megabyte file, to the same 256 bits: 64 lowercase hex characters. Change one byte of the input and roughly half the output bits flip. That property is what makes it useful as a fingerprint.

  • No API key
  • 64 hex characters
  • JSON, text or file
  • SHA-512 included

Hash a string

POST/sha256_hash

https://aisenseapi.com/services/v1/sha256_hash

Hash a string

curl -X POST https://aisenseapi.com/services/v1/sha256_hash \
  -H "Content-Type: application/json" \
  -d '{"data":"Hello world"}'
{"sha256_hash":"64ec88ca00b268e5ba1a35678a1b5316d212f4f366b2477232534a8aeca37f3c"}

That digest is a constant. Any correct SHA-256 implementation anywhere in the world gives the same 64 characters for the bytes Hello world, which is exactly why it works as a shared identifier between systems that never talk to each other.

Three input styles are accepted. A JSON body with a data field, as above. A raw request body sent as plain text, which is convenient when the content contains quotes or newlines you would rather not escape into JSON. Or a file uploaded as multipart/form-data, in which case the file bytes are hashed, not the form wrapper.

Response fields

FieldTypeDescription
sha256_hashstringExactly 64 characters, lowercase hex, always that length regardless of input size. An empty input still produces a digest, so a 64-character response is not proof that you sent what you meant to send.

Input is treated as bytes. Text is hashed as UTF-8, so accented characters and emoji contribute their encoded bytes rather than any code point abstraction. If your local implementation encodes the same string as UTF-16 or Latin-1 you will get a different digest, and the encoding is the first thing to check when two systems disagree.

SHA-512 on the same input

POST /sha512_hash takes the same request shapes and returns 128 hex characters instead of 64. The example response below is truncated for reading.

curl -X POST https://aisenseapi.com/services/v1/sha512_hash \
  -H "Content-Type: application/json" \
  -d '{"data":"Hello world"}'
{"sha512_hash":"b7f783baed8297f0db917462184ff4f08e69c2d5e5f79a942600f9725f58ce1f29c18139bf80b06c0fff2bdd34738452ecf40c48..."}

SHA-512 is not simply a longer SHA-256. It works on 64-bit words, which on 64-bit hardware often makes it faster per byte than SHA-256 despite producing twice the output. Pick SHA-256 when you need to interoperate with the wider ecosystem, which overwhelmingly defaults to it, and SHA-512 when a specification or an existing dataset asks for it.

Compare against an expected digest

POST /hash_verify takes data and an expected hash and reports whether they match. The comparison is constant-time, so the response takes the same time whether the first character differs or only the last one. Comparing digests with an ordinary string equality that exits at the first mismatched character leaks, through timing, how much of a guess was correct.

curl -X POST https://aisenseapi.com/services/v1/hash_verify \
  -H "Content-Type: application/json" \
  -d '{"data":"Hello world","hash":"64ec88ca00b268e5ba1a35678a1b5316d212f4f366b2477232534a8aeca37f3c"}'
{"match":true,"algorithm":"sha256","computed":"64ec88ca00b268e5ba1a35678a1b5316d212f4f366b2477232534a8aeca37f3c"}

The algorithm is inferred from the length of the hash you supply, so a 64-character hex string is read as SHA-256 and a 128-character one as SHA-512. The computed value comes back on a mismatch too, which makes the difference visible instead of leaving you with a bare false.

Not for passwords

Do not store passwords as SHA-256 digests. SHA-256 is designed to be fast, and fast is the wrong property for password storage: commodity hardware computes billions of SHA-256 digests per second, so a stolen table of unsalted digests falls to a dictionary attack quickly. Use a deliberately slow key derivation function instead - bcrypt, scrypt or Argon2 - each of which is built with a tunable work factor and per-password salting.

Adding a salt to SHA-256 yourself is a partial fix at best. It defeats precomputed rainbow tables but does nothing about raw guessing speed, which is the part that matters. The same caution applies to any other fast hash, including SHA-512.

Common uses

Download integrity

Publish the digest of a release file, then have the client hash what it received and compare. A truncated or tampered download will not match.

Content addressing

Key a cache or object store by the digest of the content. Identical bytes land on the same key, and duplicate uploads collapse for free.

Commit-style identifiers

Hash a serialised record, including a reference to its parent, to get a short stable id for a version. Chaining those digests makes any edit to earlier history detectable.

Signature building blocks

Digital signature and HMAC schemes sign a digest rather than the whole message. SHA-256 is the default hash in most of them, so this endpoint reproduces the intermediate value when you are debugging one.

Change detection

Store the digest of a config file or an API payload and re-hash on the next poll. A different digest is a precise signal that something changed, without diffing the content.

Privacy and limits

The input travels in the POST body, not the URL, so it does not appear in request paths. Even so, a hash is not encryption and the plaintext reaches this service before it is hashed. SHA-256 is a handful of lines in every standard library, so keep genuinely confidential input inside your own process and use this endpoint for testing, tooling and content you are comfortable sending.

The service-wide limit is 5000 requests per IP per 24 hours. No API key and no account are required.
