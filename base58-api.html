Transform - Encoding

Base58 API

Base58 is base64 with the ambiguous characters removed. There is no 0, no capital O, no capital I and no lowercase l, and no punctuation at all, so a string can be read aloud, retyped from a screenshot and selected with one double-click without anything going wrong.

  • No API key
  • No 0 O I l
  • No punctuation
  • Bitcoin alphabet

Encode

POST/base58_encode

https://aisenseapi.com/services/v1/base58_encode

Encode a string

curl -X POST https://aisenseapi.com/services/v1/base58_encode \
  -H "Content-Type: application/json" \
  -d '{"data":"Hello world"}'
{"base58_encoded_data":"JxF12TrwXzT5jvT"}

The body does not have to be JSON. A raw request body is encoded byte for byte, which is the easier route for binary input:

curl -X POST https://aisenseapi.com/services/v1/base58_encode \
  -H "Content-Type: text/plain" \
  -d 'Hello world'
{"base58_encoded_data":"JxF12TrwXzT5jvT"}

Because a raw body is valid input, a JSON body with an empty or missing data field is not an error. It is encoded as the literal text you sent: {"data":""} returns {"base58_encoded_data":"XXz9JdRpxdkbCF6"}, which decodes back to the eleven characters of that JSON, not to an empty string. Check that the field you are filling in is actually populated before you trust a result.

Decode back to bytes

Send the encoded string to /base58_decode and you get the original bytes back.

curl -X POST https://aisenseapi.com/services/v1/base58_decode \
  -H "Content-Type: application/json" \
  -d '{"data":"JxF12TrwXzT5jvT"}'
Hello world

The decoder always answers with the raw bytes as application/octet-stream, together with Content-Disposition: attachment; filename="decoded_data.bin". That header is why a browser offers a download instead of printing the result, and why command line tools are the comfortable way to use this endpoint. Redirect the body somewhere useful with -o out.bin or pipe it into xxd.

This is the one place base58 and base64 behave differently on this service. /base64_decode varies its response on the Accept header and can hand back text/plain or a JSON object with type and decoded_data. /base58_decode ignores Accept and returns the octet stream in every case, so do not write a client that expects JSON here.

Response fields and errors

FieldTypeDescription
base58_encoded_datastringReturned by /base58_encode. Contains only characters from the 58 character alphabet, with no padding and no trailing marker.
errorstringReturned with HTTP 400 when the decoder is given something outside the alphabet.

Any character the alphabet does not contain fails the whole request. A stray 0, a capital O, a capital I, a lowercase l or a space is enough:

curl -X POST https://aisenseapi.com/services/v1/base58_decode \
  -H "Content-Type: application/json" \
  -d '{"data":"Hello0"}'
{"error":"Invalid Base58 input."}

There is no lenient mode and no auto correction. The decoder will not quietly read a capital O as a zero for you, because guessing is exactly the failure base58 exists to prevent.

Why the alphabet drops four characters

The base58 alphabet is the digits 1 to 9, the uppercase letters without I and O, and the lowercase letters without l. That is 58 symbols. Three decisions follow from it.

  1. Nothing looks like anything else

    In most fonts the digit 0 and the letter O are near identical, and the capital I and the lowercase l are frequently the same glyph. Base64 contains all of them, so a base64 string cannot be safely dictated over a phone, copied off a printed page or read out of a photo. Base58 removes the collisions instead of asking the reader to be careful.

  2. No punctuation, so selection and wrapping are safe

    Base64 uses +, / and =. Those characters need percent-encoding in a URL path, they break a double-click selection into pieces in most editors and terminals, and a mail client is free to wrap or linkify around them. A base58 string is alphanumeric from end to end, so one double-click grabs all of it, a line break cannot split it at a meaningful boundary, and it drops into a URL path or a filename with no escaping.

  3. The value is a number, not a byte stream

    Base64 slices the input into six bit groups. Base58 treats the whole input as one large integer and repeatedly divides it by 58, because 58 is not a power of two. That is why there is no padding character: the output length simply follows the size of the number.

This combination is why base58 became the format for Bitcoin addresses, IPFS CIDv0 hashes, and private key and public key exports across a range of tools. Those are strings people genuinely do retype, photograph and read aloud, and where one misread character sends value to nowhere.

Leading zero bytes

Treating the input as a single number has one consequence worth knowing about. A leading zero byte adds nothing to a number, so it would vanish on the way through. Base58 handles it by writing one 1, the first symbol in the alphabet, for each leading zero byte, and the decoder puts them back:

printf '\x00\x00Hi' | curl -X POST https://aisenseapi.com/services/v1/base58_encode \
  -H "Content-Type: application/octet-stream" --data-binary @-
{"base58_encoded_data":"116Wc"}

Decoding 116Wc returns four bytes: two zero bytes followed by Hi. This is the same rule that makes a Bitcoin mainnet address start with a 1, since its version byte is zero. If you are round tripping fixed width binary, count the leading 1 characters rather than assuming a length.

What base58 costs you

Base58 is not a free upgrade over base64. Two things get worse.

It is longer. Each character carries log2(58) bits, roughly 5.86, against exactly 6 for base64, so a long input comes out around two percent bigger. Short inputs can go the other way because base58 has no padding, which is why eleven bytes of Hello world become fifteen base58 characters against sixteen base64 characters, but the asymptotic direction is against base58.

It is slower. Base64 is bit shifting and runs in linear time. Base58 is repeated big integer division, which is quadratic in the length of the input. On a wallet address or a hash the difference is invisible. On a megabyte of image data it is not, and no base58 implementation is built for that. Encode bulk payloads with base64 and keep base58 for the short, human-facing identifiers it was designed for.

Note also that this is the Bitcoin alphabet, which is the common one but not the only one. Ripple and Flickr both defined different orderings. If a value from another system fails to decode here, check the alphabet before assuming the data is corrupt.

Common uses

Codes read over the phone

Support reference numbers, device pairing codes and recovery identifiers that a person will say out loud or type from a screen, with no 0 against O confusion to resolve.

Inspecting a wallet address

Decode a Bitcoin address or another base58 key export to its raw bytes so you can look at the version byte, the payload and the checksum yourself.

Reading IPFS CIDv0 hashes

A CIDv0 is a base58 encoded multihash. Decode it to get at the hash function prefix and digest without pulling in a full IPFS library.

Identifiers in URL paths

The output is alphanumeric, so it goes straight into a path segment or a filename with no percent-encoding and no + or / to escape.

Tokens pasted into chat

A base58 string survives double-click selection and line wrapping intact, so it arrives in one piece when someone copies it out of a terminal and into a message.

Privacy and limits

Base58 is an encoding, not encryption. Anyone holding the string can decode it. Never use it to hide a secret, and never send anything sensitive through an encoder you do not control.

Data travels in the POST body rather than the URL, so it does not end up in request paths. The service-wide limit is 5000 requests per IP per 24 hours, and no key or account is needed.
