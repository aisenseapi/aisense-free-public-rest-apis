Time - Timestamps

Unix Timestamp API

The current moment as a number. A Unix timestamp is the count of whole seconds since midnight UTC on 1 January 1970, and this endpoint hands you the server's reading of it. Three shapes are available: whole seconds, the same instant with a microsecond fraction, and an ISO 8601 string.

  • No API key
  • Always UTC
  • Seconds or microseconds
  • One GET request

Read the clock

GET/timestamp

https://aisenseapi.com/services/v1/timestamp

Read the current time

Whole seconds, which is what most systems mean by "a timestamp":

curl https://aisenseapi.com/services/v1/timestamp
{"timestamp":1787171289}

The same instant with a microsecond fraction:

curl https://aisenseapi.com/services/v1/microtimestamp
{"microtimestamp":1787171289.888783}

The same instant as a human-readable ISO 8601 string:

curl https://aisenseapi.com/services/v1/datetime
{"datetime":"2026-08-19T20:28:10+00:00"}

Response fields

FieldTypeDescription
timestampintegerWhole seconds since the Unix epoch, UTC. Ten digits until November 2286.
microtimestampnumberThe same count with a fractional part to microsecond resolution.
datetimestringISO 8601 with an explicit offset, UTC by default.

The datetime endpoint also takes a fixed offset as a path segment, written as four digits with an optional leading sign:

curl https://aisenseapi.com/services/v1/datetime/0200
{"datetime":"2026-08-19T22:40:30+02:00"}

Accepted values run from -1200 to 1200. Anything outside that range, and anything that is not four digits, falls back to +00:00 rather than returning an error, so check the offset in the response if you passed one. The offset is a fixed shift, not a timezone: it does not know about daylight saving. For named zones see the timezone list on the Time APIs page.

Why ask a server for the time

Every machine already has a clock, so an endpoint that returns the time looks redundant until the clocks disagree. They do, constantly.

  1. Clocks drift

    A cheap oscillator loses or gains a few seconds a week. A virtual machine that was suspended and resumed can come back badly off. NTP fixes this when it is running and reachable, which on containers, embedded boards, CI runners and locked-down networks it often is not.

  2. Drift breaks time windows

    While building this project we hit a machine that was over a minute off. That is nothing to a human and fatal to software: signed requests carry a timestamp and are rejected outside a tolerance of a few seconds, one-time codes expire, and any API that enforces a freshness window sees a valid request as a replay or as coming from the future. The failure looks like a bad secret, not a bad clock, which is what makes it expensive to debug.

  3. A neutral reading settles it

    When both sides read the same third clock, the question stops being whose machine is right. Call the endpoint before you sign, or compare it against the local clock and refuse to run if the gap is too wide. Either way you turn a silent, intermittent failure into a number you can assert on.

This is a reading over the network, so treat it as accurate to roughly the round trip, not to the microsecond. It is a sanity check and a shared reference point, not a substitute for NTP on a host that needs real synchronisation.

Seconds, microseconds and moving a moment

Use whole seconds for anything a person will look at or a database will store as a date: expiry checks, created-at columns, cache keys, log fields. Second resolution is what most protocols expect and it keeps the value a tidy integer.

Reach for /microtimestamp when a second is too coarse to be useful. Two things happen inside the same second more often than you would guess, and if you stamp both with whole seconds you lose the order between them for good. The fraction also lets you measure short durations: take a reading, do the work, take another, subtract. Note that the fraction is resolution, not accuracy - network latency dominates anything below a few milliseconds.

The reason the plain integer keeps winning is that it is the cheapest possible way to move a moment between systems. Ten ASCII digits, no separators, no timezone suffix, no locale, no parser to disagree with. It fits in a URL, a query parameter, a filename, an environment variable, a signed header or a 32-bit column, and it survives every serialisation format unchanged. An ISO 8601 string is friendlier to read and strictly more work for a machine to agree on.

Everything here is UTC, which removes a whole class of bugs. There is no hour that happens twice in autumn and no hour that never happens in spring, so arithmetic on these values is just arithmetic. Convert to a local zone at the last moment, for display only.

To go the other way, or to translate a value you already have, POST /timestamp_convert takes either a Unix timestamp or a date string, detects which it got, and returns the input, the detected type, and the same instant as a timestamp, an ISO 8601 datetime, an RFC 2822 string and a UTC datetime. It is documented with the rest of the clock endpoints on the Time APIs page.

Common uses

Signing requests

Read the server clock immediately before building an HMAC signature so the timestamp inside it lands within the receiver's tolerance window.

Drift checks

Have a startup probe or CI step compare the local clock against the endpoint and fail loudly when the gap passes a few seconds, instead of letting the symptom surface as authentication errors later.

Ordering events

Stamp log lines or queue messages from several workers with /microtimestamp so two events in the same second still sort correctly when the streams are merged.

Shared expiry

Compute cache TTLs and token lifetimes from one clock, so every node agrees on the exact second an entry dies rather than each expiring on its own reading.

Thin clients

Give a shell script, a browser page or an embedded device a correct time without shipping a date library or trusting a battery-backed RTC.

Privacy and limits

These endpoints take no input beyond the optional offset, so there is nothing about the caller in the request to store. The response depends only on the server clock.

Responses are the current time by definition, so do not put them behind a cache or a CDN rule that would serve a stale value. The service-wide limit is 5000 requests per IP per 24 hours, which is generous for signing and drift checks and not intended as a polling loop.
