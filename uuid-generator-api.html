UUID Generator API

One GET request returns a fresh version 4 identifier in the canonical 8-4-4-12 lowercase hex form. Ask for it as uuid or, under the name the Windows and .NET world uses, as guid. Same kind of value, different key in the JSON.

  • No API key
  • Version 4
  • Plain GET request
  • 36 characters

Generate an identifier

GET/uuid

GET/guid

https://aisenseapi.com/services/v1

Get an identifier

curl https://aisenseapi.com/services/v1/uuid

{"uuid":"11ce9c91-0065-49a2-9864-ab5722a05969"}

The GUID endpoint returns the same kind of value under the other name:

curl https://aisenseapi.com/services/v1/guid

{"guid":"ddf203bc-4b5a-4aec-9867-761bfaaa1bbe"}

There is no request body, no query string and no header to set, so pasting either URL into a browser address bar is a complete test.

Response fields

FieldTypeDescription
uuidstringReturned by /uuid. A version 4 identifier, 36 characters, lowercase hex in five hyphen-separated groups.
guidstringReturned by /guid. Identical format and generation; only the JSON key differs, matching the name used by Windows, .NET and SQL Server tooling.

Each call returns a new value. Nothing is stored, so the same identifier is never handed out twice and there is no way to ask for one back.

Inside a version 4 identifier

A UUID is 128 bits. The canonical text form writes those bits as 32 lowercase hex digits split 8-4-4-12 by hyphens, which is where the 36 character length comes from. Two of the groups are not fully random, and you can read that straight off the samples above.

  1. The version nibble

    The third group starts with the version digit. In 11ce9c91-0065-49a2-9864-ab5722a05969 that is the 4 in 49a2, and it says the value came from randomness rather than from a timestamp or a MAC address.

  2. The variant bits

    The fourth group starts with a digit in the range 8 to b. Both samples begin that group with 9. These two bits mark the layout defined by RFC 4122 and its successor RFC 9562.

  3. The remaining 122 bits

    Version and variant consume six bits, leaving 122 drawn at random. That is roughly 5.3 followed by 36 zeros worth of distinct values. You would need to mint identifiers on the order of a billion billion before a single repeat became an even bet, so in ordinary application volumes collisions are not something to design around.

Why random, and what it costs

The reason to reach for a version 4 identifier is that nobody has to be asked for it. There is no central counter, no sequence to lock, no round trip to a database to find out what the next number is. Any number of machines can mint identifiers at the same moment and still not step on each other, which is exactly what distributed systems, offline-first clients and autonomous agents need: an actor can name a thing before anyone else has heard the thing exists.

That independence is paid for in three currencies, and it is worth knowing the price before you make one a primary key.

  • Size. 36 characters as text, against a handful of digits for an integer. Multiplied across every row, every index entry, every foreign key and every log line, that adds up.
  • No order. Random identifiers carry no timestamp, so sorting by id is meaningless. If you need to know what was created first you need a separate created-at column.
  • Scattered writes. Because consecutive inserts land at random points in the key space, a B-tree index on a random primary key touches pages all over the file instead of appending at the end. On write-heavy tables that costs cache locality and page splits. A common answer is to keep an internal sequential key for storage and expose the UUID as the external, shareable identifier.

Common uses

Idempotency keys

Mint one before sending a POST and attach it to the request. When a timeout forces a retry, the server recognizes the repeat and does not charge the card twice.

Correlation across services

Stamp an incoming request with a UUID and carry it through every downstream call and log line, so one grep reassembles the whole path.

Offline-first clients

A mobile app or field device creates records with no network, then syncs. Locally generated identifiers merge without renumbering anything.

.NET and Windows interop

Call /guid when the receiving system speaks in GUIDs. The value drops straight into a System.Guid or a uniqueidentifier column.

Test fixtures

Give each test run unique record names and bucket keys so parallel runs never collide on shared infrastructure.

Privacy and limits

These identifiers are generated on our server and travel back to you over the network. That is fine for record keys, correlation IDs and test data. It is not fine for cryptographic key material, session tokens or password salts: generate those locally, inside the process that will use them.

Nothing about the request is retained beyond ordinary rate limiting, and the response carries no trace of who asked. The service-wide limit is 5000 requests per IP per 24 hours, which is generous for interactive use but not a substitute for a local UUID library in a hot loop. Every mainstream language ships one, and calling it costs no network at all.
